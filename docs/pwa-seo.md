# PWA & SEO

## Progressive Web App

- `public/manifest.json` declares the app name ("Louw Swart // Portfolio"), matching dark `theme_color` and `background_color` values (`#080a20`, matching `black-russian`), `display: standalone`, icons in three purposes (192/512), and three `shortcuts` (Experience, Travel, Contact) for the OS-level app icon long-press menu. `standalone` is intentional: the portfolio benefits from an installed app window without treating ordinary page content as an immersive fullscreen experience, and the dark background avoids a white flash while the app launches. The manifest is linked from `_document.tsx` via `<link rel='manifest'>`.
- **A known Chromium defect leaves a white band behind the Android gesture bar, and it is deliberately not worked around.** Installed apps coloured the status bar from `theme_color` but left the navigation bar at the platform default. The fix merged into Chromium `main` on 2026-08-06 and colours that bar from `theme_color` — already `#080a20` here — so nothing in this repository needs to change. It reproduces in Chrome and Brave, not Firefox. See [D-260815i](decisions.md#d-260815i--wait-for-the-chromium-fix-instead-of-working-around-the-android-navigation-bar).
- **`background_color` covers only the launch splash; the page canvas must match once CSS loads**, or the two disagree at the moment the splash hands over. It does **not** address the gesture-bar band above — that was what the canvas change was written for and it did not work, since the browser paints an installed app's navigation bar itself. [Styling & Theming](styling-theming.md#the-document-canvas-background) covers the canvas, and its mechanism is commented in [`global.css`](../src/styles/global.css); [D-260815d](decisions.md#d-260815d--paint-the-document-canvas-on-html-not-on-body) records the mistaken premise.
- **Icons come in three purposes, each its own file.** `any` (192/512) is opaque navy and fills the frame, `maskable` (192/512) keeps its artwork inside the 80%-diameter safe circle, and `monochrome` (192/512) is a transparent silhouette for Android's themed icons. Sharing one file between `any` and `maskable` is what produced a white disc on the Android splash — see [D-260815e](decisions.md#d-260815e--generate-the-pwa-icon-and-splash-set-from-one-vector-master).
- `_document.tsx` also declares a full matrix of `apple-touch-startup-image` `<link>` tags — **42 of them, 21 device classes × 2 orientations** — generated by [`AppleSplashLinks`](components.md) from a single table of device points and pixel ratios, plus standard favicons and an `apple-touch-icon`. Each matches an exact `device-width`/`device-height`/`-webkit-device-pixel-ratio` triple, so **a device class with no entry gets no splash at all**; iOS has no manifest-driven fallback, and `background_color` does not apply there. Every asset is generated from `public/images/ouwl.svg` with the owl at 35% of the short edge on `#080a20`.
- **`yarn icons:generate` (`scripts/generate-pwa-icons.mjs`) rebuilds every manifest icon and splash image from `ouwl.svg`.** It reads `SPLASH_DEVICES` straight out of `AppleSplashLinks.tsx` via the TypeScript compiler API — the same approach `css-vars:generate` uses for `colors.ts` — so the splash matrix and the device table that drives it cannot drift apart the way the pre-2026-08-15 set did. The three favicon files in `public/images/manifest-icons/` (`favicon-16x16.png`, `favicon-32x32.png`, `favicon-196x196.png`) predate this script and are outside what it touches. The owl-scale constants (`ANY_SCALE`, `MASKABLE_SCALE`, `SPLASH_SCALE` in the script) were recovered by measurement against the committed assets rather than carried over from an original — the generator that produced today's set was never itself committed, and is gone.
- **`yarn icons:check` (CI, gated the same as `css-vars:check`) verifies the committed assets against what the generator would produce now** — regenerating every file in memory and diffing it against what's on disk, plus flagging any `apple-splash-*.png` with no matching `SPLASH_DEVICES` entry (orphaned by a removed device). **This is internal consistency only, not device coverage.** It cannot notice that Apple has shipped a screen size absent from the table entirely — there is no source to check that against — so it catches a hand-edit to the table without regenerating, or a regenerated asset that was never committed, not a genuinely new device going unrecognised. See [D-260821i](decisions.md#d-260821i--rely-on-manual-review-for-splash-device-coverage-not-an-automated-check).
- **Device coverage is reviewed by hand twice yearly, in mid-June and mid-October, through the maintainer's calendar rather than CI.** June catches the spring iPad and WWDC window; October follows the September iPhone launch after specifications have settled. Run the same review after an iPhone or iPad-family announcement outside those windows. A no-change review is recorded in the calendar reminder, not as a repository-only documentation change. See [D-260822c](decisions.md#d-260822c--prompt-splash-device-coverage-review-from-the-calendar-not-ci).

### Scheduled splash-device coverage review

Use this prompt for the calendar review:

> Perform the scheduled Apple splash-device coverage review. Read this document and [D-260821i](decisions.md#d-260821i--rely-on-manual-review-for-splash-device-coverage-not-an-automated-check) first. Research currently shipped iPhone and iPad display specifications using Apple sources. Compare each distinct portrait `(width, height, -webkit-device-pixel-ratio)` triple with `SPLASH_DEVICES` in `src/components/shared/AppleSplashLinks.tsx`; a model sharing an existing triple needs no entry. Do not infer a triple from a neighbouring model or treat a third-party device list as authoritative. Report every missing triple with its Apple source, or clearly report that none are missing. Do not change repository files unless explicitly asked to implement confirmed additions.

If confirmed additions are requested, update the table, run `yarn icons:generate`, then run `yarn icons:check` before proposing the change.

- **Every production build generates the service worker; development never does.** `next.config.js` wraps the config with [Serwist](https://serwist.pages.dev/) whenever `NODE_ENV` is `production`, and there is no flag to set. Since `@serwist/next` is ESM-only, the config exports an async function and dynamically `import()`s it only in that branch — which is also what keeps a webpack config out of `next dev`; see [D-260807a](decisions.md#d-260807a--generate-the-service-worker-in-every-production-build-never-in-development) for why that ordering is load-bearing rather than stylistic.
- The worker's source is `service-worker/index.ts`, a separate TypeScript project (`webworker` and `dom` libs cannot mix in one `tsc` run). CI type-checks that project separately, runs the production build, and verifies it emits a non-empty `public/sw.js` — gitignored, a build artefact rather than source — with `pages/_offline.tsx` precached and served as the fallback for uncached routes while offline.
- **Runtime caching is limited to same-origin application requests.** Images use a stale-while-revalidate strategy and other application requests use a network-first strategy; third-party requests are not intercepted. This keeps caching behaviour predictable as external integrations change.
- **Page HTML is not precached** — the manifest covers `/_next/static/**` and everything in `public/` except the 42 Apple splash images (below). So a page you have visited works offline because the same-origin `NetworkFirst` cached it in passing, and a page you have not falls back to `/_offline`. The fallback reaches the network path only because `runtimeCaching` is non-empty: Serwist attaches it to those handlers and skips the wiring entirely when the option is absent.
- **The 42 Apple splash images are excluded from the precache manifest, as of 2026-08-21.** iOS fetches at most one of them directly at launch — outside any fetch the service worker's `runtimeCaching` list could intercept — so precaching all of them bought roughly 1.6 MB into every installed app to use one file. `next.config.js` supplies `additionalPrecacheEntries` to `withSerwistInit` itself, reproducing @serwist/next's own public-directory scan (content-hashed `{url, revision}` entries) minus files matching `apple-splash-\d+-\d+\.png`. That duplication isn't a shortcut: `@serwist/next` exposes `globPublicPatterns` for what it scans from `public/`, but only as positive include patterns — no exclude option — and the underlying `glob` package dropped `!`-prefixed pattern negation in v6, so there is no way to subtract from it from outside. Supplying `additionalPrecacheEntries` at all skips the built-in scan entirely, which is what makes reproducing it necessary rather than optional. **Whether iOS's home-screen splash still renders offline after this change is not verified by anything in this test suite** — `apple-touch-startup-image` is WebKit-only, so Chromium-based Playwright cannot observe it, and public documentation of how (or whether) that mechanism interacts with a page's own service worker cache is thin and inconsistent. It was checked by hand instead, on an iOS Simulator rather than physical hardware — installed to the home screen, force-quit, relaunched with networking disabled — and the splash still rendered; see [D-260821h](decisions.md#d-260821h--reproduce-the-public-directory-precache-scan-to-exclude-the-apple-splash-images) for the exact method and its limits.
- **`/_offline` is precached by an entry the worker adds by hand**, keyed on the build timestamp, because the generated manifest carries only that page's JavaScript chunk — a prerendered document lives under `.next/server/`, which the Serwist plugin excludes. Without it `matchPrecache` finds nothing and the fallback silently produces no response, which is how it behaved until 2026-08-15. See [D-260815g](decisions.md#d-260815g--precache-the-_offline-document-which-the-build-manifest-omits).
- `mobile-web-app-capable` / `apple-mobile-web-app-capable` meta tags are set unconditionally, independent of whether the service worker build is active.
- **The manifest and referenced assets are covered by the [browser regression suite](development.md#browser-regression-suite)**, including the icon pair Chrome requires before it offers installation. Browser coverage also checks registration and offline behaviour in an isolated project. The exact test design and cache configuration are maintained privately.

## SEO / meta tags

- **Shared per-page metadata**: every content route renders `Seo` (`components/shared/Seo.tsx`) once with its title, path and description. `getSeoMetadata()` turns that one page-level source into the full title (`"{Page Name} // Louw Swart"`), canonical URL, description, Open Graph and Twitter title/URL/description/image values. This prevents inner routes from inheriting homepage social metadata during direct loads or client navigation. The shared portfolio image is the default, while the component accepts a page-specific image when one is added later.
- `_app.tsx` owns only genuinely app-wide head content: the viewport and generated font custom properties. Search and social metadata belongs to each route. Obsolete keyword metadata has been removed rather than duplicated in the shared component.
- **Every content page's `title` and description are a `const` in the page file itself**, not a fixture import — `contact.tsx`, `portfolio.tsx` and `travel.tsx` previously imported `description` from `@fixtures/contact`/`@fixtures/portfolio`/`@fixtures/travel`, while `index.tsx` and `experience.tsx` already defined it locally. All five now follow the local pattern, so the metadata a visitor and a crawler see sits next to the markup that produces it rather than split across two files. See [D-260822e](decisions.md#d-260822e--colocate-seo-copy-with-its-page-and-give-images-their-own-alt-text).
- **The `Seo` `title` prop is a distinct, keyword-bearing phrase, not the one- or two-word route/nav label** (`Front-End Engineer`, `Front-End & Full-Stack Experience`, `Freelance Web Design Portfolio`, `Places I’ve Been`, `Get In Touch`) — each combines with the `"{Page Name} // Louw Swart"` template to describe the page's content rather than only its position in the nav. `Header`'s on-page `<h1>` text is unchanged and still matches the nav label (`nav.tsx`'s `menuItems`); only the `<title>`/social title diverged from it.
- `experience.tsx` uses one concise description for ordinary, Open Graph and Twitter metadata rather than expanding every employer and role into an oversized social preview.
- **Error pages** (`404.tsx`, `500.tsx`) set `<meta name='robots' content='noindex, nofollow'>` to keep them out of search results.
- `_document.tsx` sets a global `author`/`application-name` and links a Mastodon `rel='me'` tag (`https://mastodon.nz/@henetiriki`) for Mastodon profile verification.

## Sitemap & robots (`next-sitemap`)

- `next-sitemap.config.js` runs as part of `yarn build` (`"build": "next build --webpack && next-sitemap"`), generating `public/sitemap.xml` and `public/robots.txt` from `siteUrl: process.env.HOST`.
- `generateIndexSitemap: false` — a single flat `sitemap.xml`, no sitemap index, appropriate for a handful of routes.
- `robotsTxtOptions.policies`: blocks every Baidu spider variant (`Baiduspider`, `baiduspider`, `Baiduspider+`, `-video`, `-image`) site-wide, disallows `/static` for all other user agents, and otherwise allows everything.
- The generated `public/robots.txt` is checked into git (not gitignored, unlike `sitemap.xml`/`sw.js`) — it's committed output rather than a purely ephemeral build artefact, so a change to a route disallow or a spider block arrives as a reviewable file diff rather than only as a config edit.

## AI-agent discovery (`llms.txt`)

- `public/llms.txt` is served directly at `/llms.txt` as a concise Markdown overview of the portfolio and its five canonical content routes. Keeping it as a static public asset avoids sending Lighthouse and other clients through the comparatively large custom 404 response.
- The file follows the emerging `llms.txt` convention with a required H1, a short blockquote summary and described links. It is a discovery aid, not an access-control or model-training permission mechanism; crawler policy remains in `robots.txt`.
- Only already-public portfolio information is included. Private contact details and anti-automation implementation details do not belong in this file.

## Contact abuse protection

Distinct from crawler SEO, automated-abuse protection is applied to contact submissions. It has no bearing on how search engines see the site; see [Security](security.md#contact-protection) and [Contact Feature](contact-feature.md).

## Misc head-adjacent behaviour

- Image preloading is restricted to `FixedBackground`, the deliberate full-viewport LCP image. The header-adjacent `content-top` wave uses `loading='eager'` because Next can identify it as LCP, but it is not preloaded; lower decorative waves and the 40px navigation logo remain lazy/normal priority. Portfolio cards retain grid-accurate `sizes` without being preloaded.
- **`alt` text describes the image rather than repeating the visible title or link text next to it.** The 40px navigation `Logo` reads `'Ouwl.house — home'` rather than `'Ouwl'`; each `PortfolioItem` in `@fixtures/portfolio` carries its own `img.alt` describing the screenshot (site, client, and what it's for) instead of reusing the card's `title`. `PortfolioItem` (`@fixtures/types`) models this as `img: { alt, src }` rather than a flat `imageUrl`, so every portfolio image is required to have alt text of its own rather than inheriting one implicitly. See [D-260822e](decisions.md#d-260822e--colocate-seo-copy-with-its-page-and-give-images-their-own-alt-text).

- Browser protections are described at a high level in [Security](security.md).
- `public/scripts/hash-redirect.js`, loaded async from `_document.tsx`, redirects to `/` whenever the URL hash contains `#!` — a leftover guard against old hashbang-style URLs (e.g. from a pre-Next.js single-page app) being indexed or bookmarked.
