# PWA & SEO

## Progressive Web App

- `public/manifest.json` declares the app name ("Louw Swart // Portfolio"), matching dark `theme_color` and `background_color` values (`#080a20`, matching `black-russian`), `display: standalone`, icons in three purposes (192/512), and three `shortcuts` (Experience, Travel, Contact) for the OS-level app icon long-press menu. `standalone` is intentional: the portfolio benefits from an installed app window without treating ordinary page content as an immersive fullscreen experience, and the dark background avoids a white flash while the app launches. The manifest is linked from `_document.tsx` via `<link rel='manifest'>`.
- **A known Chromium defect leaves a white band behind the Android gesture bar, and it is deliberately not worked around.** Installed apps coloured the status bar from `theme_color` but left the navigation bar at the platform default. The fix merged into Chromium `main` on 2026-08-06 and colours that bar from `theme_color` — already `#080a20` here — so nothing in this repository needs to change. It reproduces in Chrome and Brave, not Firefox. See [D-260815i](decisions.md#d-260815i--wait-for-the-chromium-fix-instead-of-working-around-the-android-navigation-bar).
- **`background_color` covers only the launch splash; the page itself needs `global.css`'s canvas background to match.** The splash is painted by the OS from the manifest before any CSS exists, but once the page loads Chrome on Android colours the region behind the gesture bar from the document canvas instead — which was transparent, so it fell back to white. `html { background-color: var(--mantine-color-black-russian-4) }` resolves both to the same `#080A20`. See [D-260815d](decisions.md#d-260815d--paint-the-document-canvas-on-html-not-on-body).
- **Icons come in three purposes, each its own file.** `any` (192/512) is opaque navy and fills the frame, `maskable` (192/512) keeps its artwork inside the 80%-diameter safe circle, and `monochrome` (192/512) is a transparent silhouette for Android's themed icons. Sharing one file between `any` and `maskable` is what produced a white disc on the Android splash — see [D-260815e](decisions.md#d-260815e--generate-the-pwa-icon-and-splash-set-from-one-vector-master).
- `_document.tsx` also declares a full matrix of `apple-touch-startup-image` `<link>` tags — **42 of them, 21 device classes × 2 orientations** — generated by [`AppleSplashLinks`](components.md) from a single table of device points and pixel ratios, plus standard favicons and an `apple-touch-icon`. Each matches an exact `device-width`/`device-height`/`-webkit-device-pixel-ratio` triple, so **a device class with no entry gets no splash at all**; iOS has no manifest-driven fallback, and `background_color` does not apply there. Every asset is generated from `public/images/ouwl.svg` with the owl at 35% of the short edge on `#080a20`.
- **`yarn icons:generate` (`scripts/generate-pwa-icons.mjs`) rebuilds every manifest icon and splash image from `ouwl.svg`.** It reads `SPLASH_DEVICES` straight out of `AppleSplashLinks.tsx` via the TypeScript compiler API — the same approach `css-vars:generate` uses for `colors.ts` — so the splash matrix and the device table that drives it cannot drift apart the way the pre-2026-08-15 set did. The three favicon files in `public/images/manifest-icons/` (`favicon-16x16.png`, `favicon-32x32.png`, `favicon-196x196.png`) predate this script and are outside what it touches. The owl-scale constants (`ANY_SCALE`, `MASKABLE_SCALE`, `SPLASH_SCALE` in the script) were recovered by measurement against the committed assets rather than carried over from an original — the generator that produced today's set was never itself committed, and is gone.
- **Every production build generates the service worker; development never does.** `next.config.js` wraps the config with [Serwist](https://serwist.pages.dev/) whenever `NODE_ENV` is `production`, and there is no flag to set. Since `@serwist/next` is ESM-only, the config exports an async function and dynamically `import()`s it only in that branch — which is also what keeps a webpack config out of `next dev`; see [D-260807a](decisions.md#d-260807a--generate-the-service-worker-in-every-production-build-never-in-development) for why that ordering is load-bearing rather than stylistic.
- The worker's source is `service-worker/index.ts`, a separate TypeScript project (`webworker` and `dom` libs cannot mix in one `tsc` run). CI type-checks that project separately, runs the production build, and verifies it emits a non-empty `public/sw.js` — gitignored, a build artifact rather than source — with `pages/_offline.tsx` precached and served as the fallback for uncached routes while offline.
- **Runtime caching is a hand-written two-entry list, not Serwist's `defaultCache`, and every matcher is gated on `sameOrigin`.** A `StaleWhileRevalidate` for `/_next/image` and a `NetworkFirst` for everything else same-origin; cross-origin requests match nothing and the worker never touches them. That is a Content Security Policy decision rather than a caching one — an intercepted request is re-issued from inside the worker, where `connect-src` is the only fetch directive that applies, so `defaultCache`'s catch-all quietly made `connect-src` govern every subresource on the site. See [D-260815f](decisions.md#d-260815f--cache-only-same-origin-requests-so-the-service-worker-stops-rewriting-the-policy) and [Security](security.md#content-security-policy).
- **Page HTML is not precached** — the manifest covers `/_next/static/**` and everything in `public/`. So a page you have visited works offline because the same-origin `NetworkFirst` cached it in passing, and a page you have not falls back to `/_offline`. The fallback reaches the network path only because `runtimeCaching` is non-empty: Serwist attaches it to those handlers and skips the wiring entirely when the option is absent.
- **`/_offline` is precached by an entry the worker adds by hand**, keyed on the build timestamp, because the generated manifest carries only that page's JavaScript chunk — a prerendered document lives under `.next/server/`, which the Serwist plugin excludes. Without it `matchPrecache` finds nothing and the fallback silently produces no response, which is how it behaved until 2026-08-15. See [D-260815g](decisions.md#d-260815g--precache-the-_offline-document-which-the-build-manifest-omits).
- `mobile-web-app-capable` / `apple-mobile-web-app-capable` meta tags are set unconditionally, independent of whether the service worker build is active.
- **The manifest and every asset it or `_document.tsx` references are covered by the [browser regression suite](development.md#browser-regression-suite)**, including the 192/512 `purpose: any` icon pair that Chrome requires before it will offer to install. **Registration is covered too**, in a project of its own so the worker's precache cannot reach any other spec — the scope, the script URL, taking control, and a reload genuinely answered from the fetch handler. See [D-260815a](decisions.md#d-260815a--give-the-service-worker-its-own-playwright-project-rather-than-unblocking-it-everywhere). **Offline is covered in both directions** — `/_offline` for a route the worker has never seen, and the runtime cache for one it has — which stopped being a manual check when the runtime caching list became hand-written and therefore able to lose the fallback silently.

## SEO / meta tags

- **Shared per-page metadata**: every content route renders `Seo` (`components/shared/Seo.tsx`) once with its title, path and description. `getSeoMetadata()` turns that one page-level source into the full title (`"{Page Name} // Louw Swart"`), canonical URL, description, Open Graph and Twitter title/URL/description/image values. This prevents inner routes from inheriting homepage social metadata during direct loads or client navigation. The shared portfolio image is the default, while the component accepts a page-specific image when one is added later.
- `_app.tsx` owns only genuinely app-wide head content: the viewport and generated font custom properties. Search and social metadata belongs to each route. Obsolete keyword metadata has been removed rather than duplicated in the shared component.
- `experience.tsx` uses one concise description for ordinary, Open Graph and Twitter metadata rather than expanding every employer and role into an oversized social preview.
- **Error pages** (`404.tsx`, `500.tsx`) set `<meta name='robots' content='noindex, nofollow'>` to keep them out of search results.
- `_document.tsx` sets a global `author`/`application-name` and links a Mastodon `rel='me'` tag (`https://mastodon.nz/@henetiriki`) for Mastodon profile verification.

## Sitemap & robots (`next-sitemap`)

- `next-sitemap.config.js` runs as part of `yarn build` (`"build": "next build --webpack && next-sitemap"`), generating `public/sitemap.xml` and `public/robots.txt` from `siteUrl: process.env.HOST`.
- `generateIndexSitemap: false` — a single flat `sitemap.xml`, no sitemap index, appropriate for a handful of routes.
- `robotsTxtOptions.policies`: blocks every Baidu spider variant (`Baiduspider`, `baiduspider`, `Baiduspider+`, `-video`, `-image`) site-wide, disallows `/static` for all other user agents, and otherwise allows everything.
- The generated `public/robots.txt` is checked into git (not gitignored, unlike `sitemap.xml`/`sw.js`) — it's committed output rather than a purely ephemeral build artifact, so a change to a route disallow or a spider block arrives as a reviewable file diff rather than only as a config edit.

## AI-agent discovery (`llms.txt`)

- `public/llms.txt` is served directly at `/llms.txt` as a concise Markdown overview of the portfolio and its five canonical content routes. Keeping it as a static public asset avoids sending Lighthouse and other clients through the comparatively large custom 404 response.
- The file follows the emerging `llms.txt` convention with a required H1, a short blockquote summary and described links. It is a discovery aid, not an access-control or model-training permission mechanism; crawler policy remains in `robots.txt`.
- Only already-public portfolio information is included. Private contact details and anti-automation implementation details do not belong in this file.

## Bot protection (BotID)

Distinct from crawler SEO, and documented elsewhere: `botid` (Vercel BotID) keeps automated traffic away from the contact form specifically, and has nothing to do with how search engines see the site. See [Security](security.md#bot-protection) for the posture and [Contact Feature](contact-feature.md) for the request flow it sits in.

## Misc head-adjacent behavior

- Image preloading is restricted to `FixedBackground`, the deliberate full-viewport LCP image. The header-adjacent `content-top` wave uses `loading='eager'` because Next can identify it as LCP, but it is not preloaded; lower decorative waves and the 40px navigation logo remain lazy/normal priority. Portfolio cards retain grid-accurate `sizes` without being preloaded.

- Response headers and the Content Security Policy have moved to [Security](security.md), which covers the whole security surface in one place.
- `public/scripts/hash-redirect.js`, loaded async from `_document.tsx`, redirects to `/` whenever the URL hash contains `#!` — a leftover guard against old hashbang-style URLs (e.g. from a pre-Next.js single-page app) being indexed or bookmarked.
