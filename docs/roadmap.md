# Roadmap

Open work only. A completed item is simply removed — the merged pull request is the record that it happened, durable rationale goes to [Engineering Decisions](decisions.md), and current behaviour to the topical documentation. Items are grouped by area rather than strict priority; each should normally be delivered as its own scoped change unless a dependency is called out explicitly.

Last reviewed: 2026-09-04.

## Framework & dependency upgrades

- [ ] **Adopt the native TypeScript 7 toolchain when ecosystem support is ready — blocked.** The project now uses TypeScript 6, the supported JavaScript-based bridge release, with its configuration deprecations already removed. The 2026-08-09 TypeScript `7.0.2` trial still failed before compilation because Yarn's built-in compatibility patch expected `lib/_tsc.js`, which the native Go distribution does not ship; `typescript-eslint` also still declares a `typescript` peer range below `6.1.0` (checked through 8.69, 2026-09-03). Recheck only when Yarn supports the native distribution and TypeScript-ESLint supports its compiler API strategy; both conditions are required.

- [ ] **Upgrade Babel 7 to 8 when Jest supports it — blocked.** The app compiles with SWC and has no Babel configuration; Babel is a direct development dependency solely for Jest. `jest-config`, `@jest/transform` and `jest-snapshot` still depend on Babel 7, so follow Jest's support rather than forcing an app-irrelevant major ahead of its consumer.

- [ ] **Upgrade Node.js 24 to 26 on or after 2026-10-28.** The project follows Active LTS releases, and Node 26 does not reach that status until then. Confirm Vercel support first, then update `engines.node`, `.nvmrc` and `@types/node` together and validate installation, native dependencies, the full suite and both build modes on the new runtime. See [D-260806a](decisions.md#d-260806a--track-active-lts-nodejs-releases).

- [ ] **Drop the `@serwist/next/browserslist` resolution once the upstream pin moves.** `package.json` carries a `resolutions` entry forcing `^4.28.7` because `@serwist/next` pins `browserslist` to the vulnerable `4.28.6` exactly, and its latest release still does; see [D-260903a](decisions.md#d-260903a--force-serwistnexts-pinned-browserslist-up-to-the-patched-line). Check it at the next `@serwist/next` upgrade: if the published `dependencies` block names anything `4.28.7` or later, remove the entry, run `yarn install` and confirm `yarn npm audit --all --recursive` stays clean. An override left behind after upstream has moved is worse than none — it pins the graph to a range nobody is watching any more.

## CI & security hardening

- [ ] **Widen `lint-staged`'s prettier glob to the types `prettier` actually checks.** It is `**/*.{cjs,html,js,jsx,json,md,mjs,scss,ts,tsx}` in `package.json` — `scss` but no `css`, and no `yml`/`yaml` — while `prettier .` covers both and nothing in `.prettierignore` excludes them. The repository tracks `*.module.css` throughout `src/` and workflow YAML under `.github/`, so a styling or CI change commits unformatted and only fails at `prettier:check`, after the commit is made. Add `css`, `yml` and `yaml`; the eslint glob is correct as it stands, since ESLint does not lint either type here. Found by the documentation sweep on [D-260905b](decisions.md#d-260905b--number-the-release-ready-sequence-and-commit-before-the-review-runs), which had claimed `lint-staged` covers everything and nearly retired a formatting step on that basis — the [sequence](release-checklist.md#before-opening-the-pr)'s formatting step is the cover until this lands, and should be reconsidered once it has. **The glob string is quoted verbatim in four places and they go stale together**: `package.json` itself, [`development.md`](development.md#git-hooks)'s code block, the paragraph in [`release-checklist.md`](release-checklist.md#before-opening-the-pr) explaining why the formatting step exists, and [D-260905b](decisions.md#d-260905b--number-the-release-ready-sequence-and-commit-before-the-review-runs). Touches `package.json`, so unlike most of this section it is not a documentation-only change and takes the full CI path.

- [ ] **Upgrade ESLint off `9.39.5`.** `yarn npm audit --all` flags it as a deprecated, no-longer-supported version (moderate severity); it's a development-only dependency so there's no production exposure, but it's currently excluded from Dependabot's automated major-version updates (see `.github/dependabot.yml`'s `ignore` list) pending a coordinated config/plugin compatibility pass.

- [ ] **Reconcile the three descriptions of CI's cheap path, which all understate it.** [`release-checklist.md`](release-checklist.md#pull-request) says a documentation-only change leaves "install, `prettier:check`, `test:coverage` and the coverage upload"; [`AGENTS.md`](../AGENTS.md#deploys) says the same; and the workflow's own run-summary string says "`prettier:check` and the Jest run ran, everything else was skipped". All three omit `docs:check-links` and `agent:check-config`, which are ungated on purpose, plus the branch-name check on a pull request. The inaccuracy originates in the summary string in [`ci.yml`](../.github/workflows/ci.yml), so the fix moves in three places at once; the checklist already states the correct behaviour two paragraphs earlier and in [D-260903c](decisions.md#d-260903c--test-the-agent-configuration-in-ci-rather-than-only-parsing-it), which is what makes the contradiction visible. It dates from D-260903c making `agent:check-config` ungated. **Now worth fixing rather than noting**: `.claude/agents/` classifies as documentation-only, so that ungated step is the only thing validating the review agents' tool restriction in CI — a reader who believes the enumeration would conclude nothing checks them at all. Raised by the documentation sweep on [#265](https://github.com/henetiriki/portfolio/pull/265).

- [ ] **Review `scripts/should-skip-vercel-build.sh`'s exclusion list against what the repository now holds.** The list has not changed since it was written, while the repository has kept adding paths a visitor cannot see. Seven of the forty commits merged between 2026-08-22 and 2026-09-04 built production for such a change: `.github/workflows/` four times ([#224](https://github.com/henetiriki/portfolio/pull/224), [#225](https://github.com/henetiriki/portfolio/pull/225), [#235](https://github.com/henetiriki/portfolio/pull/235), [#248](https://github.com/henetiriki/portfolio/pull/248)), `scripts/` twice ([#260](https://github.com/henetiriki/portfolio/pull/260), [#261](https://github.com/henetiriki/portfolio/pull/261)), and `.gitignore`, `.prettierignore` and `eslint.config.mjs` together once ([#247](https://github.com/henetiriki/portfolio/pull/247)). The clearest single miss is `playwright.maps-smoke.config.ts`, the browser suite's second config, added by [#230](https://github.com/henetiriki/portfolio/pull/230) after the list had named its sibling as an individual file rather than by pattern — and that is also the reason to prefer directories to filenames when fixing this, or it goes stale the same way again. Candidates by the criterion the list [already applies](release-checklist.md#merge--deploy): `.github/`, `.husky/`, `scripts/`, `codecov.yml`, `jest.config.js`, `jest.setup.ts`, `.env.test`, `.prettierrc.json`, `.prettierignore`, `eslint.config.mjs` and `playwright.maps-smoke.config.ts`. `scripts/` earns a whole-directory exclusion despite `postinstall` running one of its generators: `css-vars:generate`'s output is gitignored and never imported, and `generate-pwa-icons.mjs` writes tracked files under `public/`, so a regeneration triggers the build through `public/` and a generator changed without one is caught by `yarn icons:check`. `.gitignore` stays un-excluded, deliberately; see the [release checklist](release-checklist.md#merge--deploy). Note the one self-reference: excluding `scripts/` excludes the gate itself, so a change to it no longer triggers the deploy that would exercise it — [D-260904b](decisions.md#d-260904b--decide-documentation-only-once-and-let-both-callers-ask-it) left this gate out of the shared classifier precisely because it cannot be exercised before a real deploy. Any change here moves in three places at once: the script, the checklist's exclusion sentence and its "what earns an exclusion" note, and `AGENTS.md`. Scope it on its own, and verify it by watching the next few merges rather than by a test.

- [ ] **Stop `postinstall` generating the IDE-only CSS variables on Vercel.** `postinstall` runs `yarn css-vars:generate`, which parses `src/styles/colors.ts` with the TypeScript compiler and writes `src/styles/mantine-custom-properties.css`. That file is gitignored and deliberately never imported — its only job is letting WebStorm resolve `var(--mantine-color-…)` references in `.module.css` files, since the real values reach the browser from `MantineProvider`; see [Styling & Theming](styling-theming.md#webstorm-css-variable-resolution-mantine-custom-propertiescss). A production build has no IDE to serve, so on Vercel the step can only cost time or fail the deploy; there is no outcome where it helps. It cannot simply move to a development-only hook: CI runs `yarn css-vars:check` immediately after `yarn install --immutable` and the check is only meaningful because `postinstall` produced the file it compares against, and each worktree depends on the same thing (see [D-260814e](decisions.md#d-260814e--let-each-worktree-install-its-own-dependencies)). The narrow fix is for the generator to no-op when `VERCEL` is set, leaving `postinstall` itself unchanged so local installs, worktrees and CI behave exactly as they do now. Put that condition inside the script rather than in the `package.json` script string, which would have to become a shell conditional and would not survive a Windows install. One failure mode to accept knowingly: if the generated file were ever imported after this lands, CI would still pass and only the Vercel build would break. Worth deciding in the same change whether `css-vars:check` still earns its CI step, since what it actually verifies is that generation from `colors.ts` is deterministic — there is no committed copy for it to catch drift against.

## Documentation weight

Raised by the proportionality audit of 2026-09-04, which compared the repository against `60bf27a`, the last human-maintained commit. Its finding: the executable machinery earns its keep on recorded evidence, and the prose around it does not. Of the 158 commits in that range, **143 touched `docs/` and 65 touched `src/`** — the site changed in 65 commits and the description of the site changed in 143. Retiring `project-history.md` was the first half and is done ([D-260904h](decisions.md#d-260904h--retire-the-history-file-and-fold-its-residue-into-the-decision-it-qualifies)); what remains is the file it left behind as the largest in the repository.

**Three steps, in this order: the bar, the unit, then the compaction.** The bar is done ([D-260905a](decisions.md#d-260905a--say-what-earns-a-decision-entry-and-do-not-enforce-it-with-a-script)) — it went first because it needed no exclusive window and stops the accumulation immediately. The unit question now comes **before** the compaction rather than after it, which reverses the order they were listed in: compacting each entry is safe only because headings never move, and folding entries into per-area ones afterwards would both rewrite the prose just squeezed and withdraw that guarantee. The compaction needs a window with no other branches open, and so would a fold; deciding the unit costs no window at all, which is what lets the compaction run once, in whatever shape the decision settles on.

- [ ] **Decide whether the unit of a decision entry should change from the change to the area.** Today one entry records one change, so the file grows linearly with the work — the shell-hygiene hook alone spans [D-260814b](decisions.md#d-260814b--enforce-shell-hygiene-with-a-hook-rather-than-a-convention), [D-260903b](decisions.md#d-260903b--empty-the-local-allowlist-and-let-the-classifier-see-every-command) and [D-260904c](decisions.md#d-260904c--narrow-the-shell-hygiene-hook-to-shell-syntax-and-check-branch-names-in-ci), each partly retiring the last. One entry per area, revised in place with a superseded trail, is the only shape where the file stops growing with every change. The cost is real: it contradicts "an entry stays as published once merged" ([D-260821j](decisions.md#d-260821j--check-internal-documentation-links-in-ci-rather-than-relying-on-the-release-sweep)) and needs a redirect anchor for every folded identifier — index noise of exactly the kind the [private-record collapse](decisions.md#private-operational-records) has just cleared twelve of, at a scale an order of magnitude larger. **It also inherits the one question [D-260905a](decisions.md#d-260905a--say-what-earns-a-decision-entry-and-do-not-enforce-it-with-a-script) left open**: that bar is prospective, so whether an entry that would not be minted today should keep its heading is undecided, and it is the same question the fold asks in another form — answer both together. Two constraints bind any verdict. [`check-doc-links.mjs`](../scripts/check-doc-links.mjs) validates in-repo anchors and runs ungated in CI, so a removed heading fails the build rather than merely rotting. And the alternative to a redirect heading per identifier is repointing every internal citation at a collective anchor and letting stale external links land there instead of at the record — which is what the private-record collapse already did, and it stated that cost rather than discovering it. [Styling & Theming](styling-theming.md#theme-srcstylesthemets) is the worked example: it cites `D-260821k` by identifier, links it to the section rather than to a heading that no longer exists, and reads no worse for it. Sample two or three areas beyond the shell-hygiene trio before deciding: if most hold a single entry, the fold buys little and still costs a redirect scheme. A "no change" verdict is a real outcome, and closes the question permanently before the compaction spends its window.

- [ ] **Compact every entry.** Squeeze each to a context sentence, the decision, the "why not X" that stops it being re-litigated, and a pull request link for the rest. Sequence the pass by inbound links rather than by date, and note that being uncited is not evidence of being worthless: [D-260809b](decisions.md#d-260809b--treat-the-contact-endpoint-as-a-stable-public-boundary) is a live constraint nobody has needed to link. Splitting the file into a live half and an archive is the wrong shape and was rejected; the anchors are why. **Headings never change** under today's unit, so every inbound anchor survives and the identifier scheme is untouched — and that guarantee is exactly what the item above may withdraw, which is why it is settled first. Not enforced by a script, for the reasons already given in [D-260905a](decisions.md#d-260905a--say-what-earns-a-decision-entry-and-do-not-enforce-it-with-a-script). **Needs a window with no other branches open**, for the same reason the retirement did.

## Documentation gaps

- [ ] **Record when a repository setting may be named publicly — blocked on a maintainer check.** The [sensitive-information section](release-checklist.md#sensitive-information) asks whether a new third-party URL is safe to publish, but says nothing about configuration values, and [D-260905b](decisions.md#d-260905b--number-the-release-ready-sequence-and-commit-before-the-review-runs) named `squash_merge_commit_message` in two public files without a rule to point at. The line proposed by the pass that cleared it: a setting is public-safe where its value is observable from outside and carries no security function, and belongs in the private runbook where it names a protection's exact configuration, an exemption, who can bypass it, or what is not monitored. That reasoning holds for this one — its effect is visible in every squash commit on public `main`, and withholding it while publicly documenting squash-only merging and the ruleset's no-bypass-actors posture would be incoherent. **Blocked because it assumes the runbook has no blanket rule making configuration values private as a class**, which is not inferable from anything public; confirm that before writing the bullet, and move the two existing mentions if it turns out otherwise.

- [ ] **Fill the gaps in both script tables — `validate`, `branch:check` and `test:e2e:maps-smoke`.** The root [`README.md`](../README.md)'s table omits all three; [`development.md`](development.md#scripts-packagejson)'s has the first two and omits `test:e2e:maps-smoke`. `yarn validate` is the one that matters most — it is the entry point the whole [release sequence](release-checklist.md#before-opening-the-pr) turns on, and a reader working from the root table would not know it exists. ## Code quality follow-ups

- [ ] **Replace `useIntersectedOnce` with `@mantine/hooks`' `useIntersection`.** The hand-rolled hook duplicates an IntersectionObserver wrapper the project already depends on. Not a drop-in swap: Mantine's hook exposes the raw `entry` on every change rather than latching once and disconnecting, so `MapWrapper` (its only consumer) would need to own that one-shot logic itself. Deferred deliberately rather than done alongside the [D-260825e](decisions.md#d-260825e--check-intersectionratio-against-the-threshold-in-useintersectedonce-not-isintersecting) threshold fix, to keep that fix minimal.

- [ ] **Consider phonetic exceptions for `useArticleAgreement`'s vowel-sound check.** `vowelSoundPattern` matches the leading letter, not the leading sound, so a future tagline word like "European" or "MBA" would get the wrong article ("an European"). The current home-page word list doesn't trigger it, and the word list is fully author-controlled with every change subject to this repo's own preview-URL manual QA, so a wrong article would be caught immediately if it ever happened — deliberately left unfixed rather than building exceptions for words that don't exist in the sequence yet.

## Content & copy

- [ ] **Decide whether the experience-entry prose moves off its flat, factual register.** The job entries in `src/fixtures/experience.tsx` are uniformly declarative ("I joined X as a Y", "I worked in the team replacing…"), while the site's framing — the home bio, the page headers, the icon-only Flight Attendant entry — carries dry wit. Staying factual costs nothing to maintain and ages well, since enthusiasm is timestamped — the Equal Experts entry opened with an "excited to start this next chapter" line that was pared back to a plain statement for exactly that reason. Going conversational is a whole-history decision, not a per-entry one, or it leaves a visible seam around 2025. Middle path if revisited: keep entries factual and past-tense by default, allow one voice sentence per entry only where there is a genuine story (the CSA no-prior-Python line is the model), and decide the seam explicitly. Raised during the 2026-08-29 copy pass and deliberately not acted on.
