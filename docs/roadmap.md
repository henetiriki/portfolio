# Roadmap

Open work only. Completed milestones are recorded in [Project History](project-history.md), durable rationale in [Engineering Decisions](decisions.md), and current behaviour in the topical documentation. Items are grouped by area rather than strict priority; each should normally be delivered as its own scoped change unless a dependency is called out explicitly.

Last reviewed: 2026-08-16.

## Framework & dependency upgrades

- [ ] **Adopt the native TypeScript 7 toolchain when ecosystem support is ready — blocked.** The project now uses TypeScript 6, the supported JavaScript-based bridge release, with its configuration deprecations already removed. The 2026-08-09 TypeScript `7.0.2` trial still failed before compilation because Yarn's built-in compatibility patch expected `lib/_tsc.js`, which the native Go distribution does not ship; `typescript-eslint` also still declares a `typescript` peer range below `6.1.0` (checked through 8.69, 2026-09-03). Recheck only when Yarn supports the native distribution and TypeScript-ESLint supports its compiler API strategy; both conditions are required.

- [ ] **Upgrade Babel 7 to 8 when Jest supports it — blocked.** The app compiles with SWC and has no Babel configuration; Babel is a direct development dependency solely for Jest. `jest-config`, `@jest/transform` and `jest-snapshot` still depend on Babel 7, so follow Jest's support rather than forcing an app-irrelevant major ahead of its consumer.

- [ ] **Upgrade Node.js 24 to 26 on or after 2026-10-28.** The project follows Active LTS releases, and Node 26 does not reach that status until then. Confirm Vercel support first, then update `engines.node`, `.nvmrc` and `@types/node` together and validate installation, native dependencies, the full suite and both build modes on the new runtime. See [D-260806a](decisions.md#d-260806a--track-active-lts-nodejs-releases).

- [ ] **Drop the `@serwist/next/browserslist` resolution once the upstream pin moves.** `package.json` carries a `resolutions` entry forcing `^4.28.7` because `@serwist/next` pins `browserslist` to the vulnerable `4.28.6` exactly, and its latest release still does; see [D-260903a](decisions.md#d-260903a--force-serwistnexts-pinned-browserslist-up-to-the-patched-line). Check it at the next `@serwist/next` upgrade: if the published `dependencies` block names anything `4.28.7` or later, remove the entry, run `yarn install` and confirm `yarn npm audit --all --recursive` stays clean. An override left behind after upstream has moved is worse than none — it pins the graph to a range nobody is watching any more.

## CI & security hardening

- [ ] **Upgrade ESLint off `9.39.5`.** `yarn npm audit --all` flags it as a deprecated, no-longer-supported version (moderate severity); it's a development-only dependency so there's no production exposure, but it's currently excluded from Dependabot's automated major-version updates (see `.github/dependabot.yml`'s `ignore` list) pending a coordinated config/plugin compatibility pass.

## Agent configuration

Raised by a 2026-09-03 review of this repository against [The AI-Native SDLC Playbook](https://claude.com/blog/the-ai-native-sdlc-playbook). These are one programme rather than four unrelated items, and are listed in the order they should be taken. The permission and Auto mode review that led the list is done — see [D-260903b](decisions.md#d-260903b--empty-the-local-allowlist-and-let-the-classifier-see-every-command).

- [ ] **Validate `.claude/` in CI.** Agent configuration is the only thing here with no regression check, and CI actively gives it the cheapest path: `.claude/**` is on the documentation-only exclusion list, so a change to the settings file holding the hook runs install, `prettier:check` and the Jest run and nothing else. Model the check on `scripts/check-doc-links.mjs` and leave it ungated for the same reason ([D-260821j](decisions.md#d-260821j--check-internal-documentation-links-in-ci-rather-than-relying-on-the-release-sweep)) — the settings file parses, each hook's `jq` program compiles, the program actually denies a sample chained command, every path a hook references exists, and `permissions.allow` is sorted as [Code conventions](../AGENTS.md#code-conventions) requires and nothing checks. The compile and deny checks are the ones that earn it: the hook is a JSON string wrapping a `jq` program wrapping a regex, and D-260814b records that it fails open, so a broken escape is silent. Revisit `.claude/`'s place on the exclusion list once there is something to run; that entry was written when the directory held only prose.

- [ ] **Promote the remaining advisory agent rules to deterministic checks, choosing each enforcement point by which agents have to obey it.** [D-260814b](decisions.md#d-260814b--enforce-shell-hygiene-with-a-hook-rather-than-a-convention) established the pattern for shell hygiene; the `git -C` ban, the [branch-name prefixes](../AGENTS.md#branch-names) and the `-F`/`--body-file` rule for commit messages and pull request bodies are still instructions only. The choice of mechanism is the substance, because **a `.claude/settings.json` hook binds Claude Code and nothing else** — no other agent reads that file, so a hook is a second belt for one tool rather than a replacement for the written rule, and the `AGENTS.md` prose has to stay either way. Where a rule must hold whoever is driving, the enforcement point is the git hook or CI, which run on the artefact rather than inside a harness: the branch prefixes are better checked against the pull request's head ref than at `git checkout -b`, which also closes the gap where a branch is created in the IDE. The Auto mode review has already narrowed this: `git stash` is covered by a classifier rule, so it needs nothing here, and [D-260903b](decisions.md#d-260903b--empty-the-local-allowlist-and-let-the-classifier-see-every-command) closed the allowlist-laundering hole that made a `PreToolUse` hook look like a safety control rather than a convention. What is left is three conventions worth enforcing as conventions, which lowers the bar for choosing CI over a hook.

- [ ] **Lint and format the edited file on write, rather than only at commit.** Every check here is whole-repo and manual — `eslint .`, `prettier .`, `tsc` across the project — so the first signal on a bad edit arrives at `.husky/pre-commit` ([Git hooks](development.md#git-hooks)) or later. A `PostToolUse` hook running `eslint --fix` then `prettier --write` on the edited path would front-load exactly what `lint-staged` already does, reusing its globs from `package.json` so there is one list rather than two — which is also what keeps the ignore lists honest, since `public/sw.js` and `next-env.d.ts` must not be rewritten to satisfy a linter. Three things to write down alongside it: it fixes and reports rather than blocking, so an auto-fix cannot fight the edit that triggered it; it binds Claude Code only, per the item above; and it does not replace `yarn eslint:check` before a pull request, because a file-scoped run cannot see cross-file rules such as `import/order` resolving `@alias/*`.

- [ ] **Move the task-shaped procedures out of `AGENTS.md` and into skills, leaving linked pointers behind.** [`AGENTS.md`](../AGENTS.md) is read in full at the start of every session, including sessions that never open a pull request, never rebase and never touch a worktree — and [Opening a pull request](../AGENTS.md#opening-a-pull-request), [Validating a change](../AGENTS.md#validating-a-change), [Working across branches](../AGENTS.md#working-across-branches) and [Worktrees](../AGENTS.md#worktrees) are each dead weight until the moment they apply. The constraint on the move is that `AGENTS.md` is deliberately the cross-tool file, so the shape is the one it already uses for `docs/`: the skill holds the procedure and `AGENTS.md` keeps a one-line pointer with a link, which another agent follows as an ordinary path. A skill that fails to trigger then degrades to a lookup rather than to silence — verify each one triggers by asking for its task several ways in a fresh session, since a skill nobody can invoke is worse than the line it replaced. A `release-ready-check` skill would also settle a live duplication, the magic phrase being defined both in `AGENTS.md` and in the [release checklist](release-checklist.md). Take this last: it rewrites a file every branch touches, which is exactly the case `AGENTS.md` says needs a window with no other branches open.

- [ ] **Record the port 3001 collision, and give `.claude/` a topical doc.** Both `.claude/launch.json` servers and the browser suite bind 3001, and `playwright.config.ts` sets `reuseExistingServer: false`, so an agent's preview server left running makes `yarn test:e2e` fail immediately on a port conflict. [D-260816g](decisions.md#d-260816g--serve-the-browser-suite-on-3001-and-leave-3000-to-next-dev) reasoned carefully about the contention on 3000 and moved the agent's servers onto the suite's own port without recording this consequence. Separately, nothing under `docs/` covers `.claude/` at all — the hook's rationale is in D-260814b and its behaviour in `AGENTS.md`, which leaves current behaviour without the topical home this project's own [documentation discipline](../AGENTS.md#documentation-discipline) asks for. Optional while the directory holds one hook; necessary once the items above land.

## Code quality follow-ups

- [ ] **Replace `useIntersectedOnce` with `@mantine/hooks`' `useIntersection`.** The hand-rolled hook duplicates an IntersectionObserver wrapper the project already depends on. Not a drop-in swap: Mantine's hook exposes the raw `entry` on every change rather than latching once and disconnecting, so `MapWrapper` (its only consumer) would need to own that one-shot logic itself. Deferred deliberately rather than done alongside the [D-260825e](decisions.md#d-260825e--check-intersectionratio-against-the-threshold-in-useintersectedonce-not-isintersecting) threshold fix, to keep that fix minimal.

- [ ] **Consider phonetic exceptions for `useArticleAgreement`'s vowel-sound check.** `vowelSoundPattern` matches the leading letter, not the leading sound, so a future tagline word like "European" or "MBA" would get the wrong article ("an European"). The current home-page word list doesn't trigger it, and the word list is fully author-controlled with every change subject to this repo's own preview-URL manual QA, so a wrong article would be caught immediately if it ever happened — deliberately left unfixed rather than building exceptions for words that don't exist in the sequence yet.

## Content & copy

- [ ] **Decide whether the experience-entry prose moves off its flat, factual register.** The job entries in `src/fixtures/experience.tsx` are uniformly declarative ("I joined X as a Y", "I worked in the team replacing…"), while the site's framing — the home bio, the page headers, the icon-only Flight Attendant entry — carries dry wit. Staying factual costs nothing to maintain and ages well, since enthusiasm is timestamped — the Equal Experts entry opened with an "excited to start this next chapter" line that was pared back to a plain statement for exactly that reason. Going conversational is a whole-history decision, not a per-entry one, or it leaves a visible seam around 2025. Middle path if revisited: keep entries factual and past-tense by default, allow one voice sentence per entry only where there is a genuine story (the CSA no-prior-Python line is the model), and decide the seam explicitly. Raised during the 2026-08-29 copy pass and deliberately not acted on.

## Performance, SEO & platform polish

- [ ] **Confirm the white band behind the Android gesture bar clears once Chrome stable ships the upstream fix.** Nothing to build — the fix merged into Chromium `main` on 2026-08-06 and colours the navigation bar from `theme_color`, already correct here. See [D-260815i](decisions.md#d-260815i--wait-for-the-chromium-fix-instead-of-working-around-the-android-navigation-bar).
  - **Earliest realistic check is late September 2026**, since `main` reaches stable in roughly four to ten weeks. Install the app on Android and confirm the region behind the gesture bar is `#080a20`.
  - **If it has not cleared by then, check the killswitch before rebuilding a workaround.** The fix ships behind `WebAppNavigationBarThemeColor`, default-on — a disabled or reverted flag would look identical to no fix at all.
  - **Two workarounds already exist and were discarded deliberately**, so neither needs rediscovering: reverting `display` to `fullscreen` (one word, costs the Android status bar permanently, iOS unaffected) and `viewport-fit=cover` (needs `env(safe-area-inset-*)` on the sticky header, the fixed scroll-to-top control, the footer's bottom band and the full-screen mobile drawer — the drawer least certain, since its close button is absolutely positioned and it could not be opened under browser automation to verify).
