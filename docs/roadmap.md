# Roadmap

Open work only. A completed item is simply removed — the merged pull request is the record that it happened, durable rationale goes to [Engineering Decisions](decisions/README.md), and current behaviour to the topical documentation. Items are grouped by area rather than strict priority; each should normally be delivered as its own scoped change unless a dependency is called out explicitly.

Last reviewed: 2026-09-06.

## Framework & dependency upgrades

- [ ] **Adopt the native TypeScript 7 toolchain when ecosystem support is ready — blocked.** The project now uses TypeScript 6, the supported JavaScript-based bridge release, with its configuration deprecations already removed. The 2026-08-09 TypeScript `7.0.2` trial still failed before compilation because Yarn's built-in compatibility patch expected `lib/_tsc.js`, which the native Go distribution does not ship; `typescript-eslint` also still declares a `typescript` peer range below `6.1.0` (checked through 8.69, 2026-09-03). Recheck only when Yarn supports the native distribution and TypeScript-ESLint supports its compiler API strategy; both conditions are required.

- [ ] **Upgrade Babel 7 to 8 when Jest supports it — blocked.** The app compiles with SWC and has no Babel configuration; Babel is a direct development dependency solely for Jest. `jest-config`, `@jest/transform` and `jest-snapshot` still depend on Babel 7, so follow Jest's support rather than forcing an app-irrelevant major ahead of its consumer.

- [ ] **Upgrade Node.js 24 to 26 on or after 2026-10-28.** The project follows Active LTS releases, and Node 26 does not reach that status until then. Confirm Vercel support first, then update `engines.node`, `.nvmrc` and `@types/node` together and validate installation, native dependencies, the full suite and both build modes on the new runtime. See D-260806a.

- [ ] **Drop the `@serwist/next/browserslist` resolution once the upstream pin moves.** `package.json` carries a `resolutions` entry forcing `^4.28.7` because `@serwist/next` pins `browserslist` to the vulnerable `4.28.6` exactly, and its latest release still does; see D-260903a. Check it at the next `@serwist/next` upgrade: if the published `dependencies` block names anything `4.28.7` or later, remove the entry, run `yarn install` and confirm `yarn npm audit --all --recursive` stays clean. An override left behind after upstream has moved is worse than none — it pins the graph to a range nobody is watching any more.

## CI & security hardening

- [ ] **Widen `lint-staged`'s prettier glob to the types `prettier` actually checks.** It is `**/*.{cjs,html,js,jsx,json,md,mjs,scss,ts,tsx}` in `package.json` — `scss` but no `css`, and no `yml`/`yaml` — while `prettier .` covers both and nothing in `.prettierignore` excludes them. The repository tracks `*.module.css` throughout `src/` and workflow YAML under `.github/`, so a styling or CI change commits unformatted and only fails at `prettier:check`, after the commit is made. Add `css`, `yml` and `yaml`; the eslint glob is correct as it stands, since ESLint does not lint either type here. Found by the documentation sweep on D-260905b, which had claimed `lint-staged` covers everything and nearly retired a formatting step on that basis — the [sequence](release-checklist.md#before-opening-the-pr)'s formatting step is the cover until this lands, and should be reconsidered once it has. **The glob string is quoted verbatim in three live places and they go stale together**: `package.json` itself, [`development.md`](development.md#git-hooks)'s code block, and the paragraph in [`release-checklist.md`](release-checklist.md#before-opening-the-pr) explaining why the formatting step exists. D-260905b holds a fourth copy, frozen in the archive and deliberately not maintained. Touches `package.json`, so unlike most of this section it is not a documentation-only change and takes the full CI path.

- [ ] **Upgrade ESLint off `9.39.5`.** `yarn npm audit --all` flags it as a deprecated, no-longer-supported version (moderate severity); it's a development-only dependency so there's no production exposure, but it's currently excluded from Dependabot's automated major-version updates (see `.github/dependabot.yml`'s `ignore` list) pending a coordinated config/plugin compatibility pass.

- [ ] **Reconcile the two descriptions of CI's cheap path, which both understate it.** [`release-checklist.md`](release-checklist.md#pull-request) says a documentation-only change leaves "install, `prettier:check`, `test:coverage` and the coverage upload", and the workflow's own run-summary string says "`prettier:check` and the Jest run ran, everything else was skipped". Both omit `docs:check-links` and `agent:check-config`, which are ungated on purpose, plus the branch-name check on a pull request. [`AGENTS.md`](../AGENTS.md#deploys) carried a third copy and now points at the checklist instead, which is one fewer place to fix rather than a fix. The inaccuracy originates in the summary string in [`ci.yml`](../.github/workflows/ci.yml), so the fix moves in two places at once; the checklist already states the correct behaviour two paragraphs earlier and in D-260903c, which is what makes the contradiction visible. It dates from D-260903c making `agent:check-config` ungated. **Now worth fixing rather than noting**: `.claude/agents/` classifies as documentation-only, so that ungated step is the only thing validating the review agents' tool restriction in CI — a reader who believes the enumeration would conclude nothing checks them at all. Raised by the documentation sweep on [#265](https://github.com/henetiriki/portfolio/pull/265).

- [ ] **Review `scripts/should-skip-vercel-build.sh`'s exclusion list against what the repository now holds.** The list has not changed since it was written, while the repository has kept adding paths a visitor cannot see. Seven of the forty commits merged between 2026-08-22 and 2026-09-04 built production for such a change: `.github/workflows/` four times ([#224](https://github.com/henetiriki/portfolio/pull/224), [#225](https://github.com/henetiriki/portfolio/pull/225), [#235](https://github.com/henetiriki/portfolio/pull/235), [#248](https://github.com/henetiriki/portfolio/pull/248)), `scripts/` twice ([#260](https://github.com/henetiriki/portfolio/pull/260), [#261](https://github.com/henetiriki/portfolio/pull/261)), and `.gitignore`, `.prettierignore` and `eslint.config.mjs` together once ([#247](https://github.com/henetiriki/portfolio/pull/247)). The clearest single miss is `playwright.maps-smoke.config.ts`, the browser suite's second config, added by [#230](https://github.com/henetiriki/portfolio/pull/230) after the list had named its sibling as an individual file rather than by pattern — and that is also the reason to prefer directories to filenames when fixing this, or it goes stale the same way again. Candidates by the criterion the list [already applies](release-checklist.md#merge--deploy): `.github/`, `.husky/`, `scripts/`, `codecov.yml`, `jest.config.js`, `jest.setup.ts`, `.env.test`, `.prettierrc.json`, `.prettierignore`, `eslint.config.mjs` and `playwright.maps-smoke.config.ts`. `scripts/` earns a whole-directory exclusion despite `postinstall` running one of its generators: `css-vars:generate`'s output is gitignored and never imported, and `generate-pwa-icons.mjs` writes tracked files under `public/`, so a regeneration triggers the build through `public/` and a generator changed without one is caught by `yarn icons:check`. `.gitignore` stays un-excluded, deliberately; see the [release checklist](release-checklist.md#merge--deploy). Note the one self-reference: excluding `scripts/` excludes the gate itself, so a change to it no longer triggers the deploy that would exercise it — D-260904b left this gate out of the shared classifier precisely because it cannot be exercised before a real deploy. Any change here moves in three places at once: the script, the checklist's exclusion sentence and its "what earns an exclusion" note, and `AGENTS.md`. Scope it on its own, and verify it by watching the next few merges rather than by a test.

- [ ] **Stop `postinstall` generating the IDE-only CSS variables on Vercel.** `postinstall` runs `yarn css-vars:generate`, which parses `src/styles/colors.ts` with the TypeScript compiler and writes `src/styles/mantine-custom-properties.css`. That file is gitignored and deliberately never imported — its only job is letting WebStorm resolve `var(--mantine-color-…)` references in `.module.css` files, since the real values reach the browser from `MantineProvider`; see [Styling & Theming](styling-theming.md#webstorm-css-variable-resolution-mantine-custom-propertiescss). A production build has no IDE to serve, so on Vercel the step can only cost time or fail the deploy; there is no outcome where it helps. It cannot simply move to a development-only hook: CI runs `yarn css-vars:check` immediately after `yarn install --immutable` and the check is only meaningful because `postinstall` produced the file it compares against, and each worktree depends on the same thing (see D-260814e). The narrow fix is for the generator to no-op when `VERCEL` is set, leaving `postinstall` itself unchanged so local installs, worktrees and CI behave exactly as they do now. Put that condition inside the script rather than in the `package.json` script string, which would have to become a shell conditional and would not survive a Windows install. One failure mode to accept knowingly: if the generated file were ever imported after this lands, CI would still pass and only the Vercel build would break. Worth deciding in the same change whether `css-vars:check` still earns its CI step, since what it actually verifies is that generation from `colors.ts` is deterministic — there is no committed copy for it to catch drift against.

## Agent configuration

Raised by a 2026-09-03 review of this repository against [The AI-Native SDLC Playbook](https://claude.com/blog/the-ai-native-sdlc-playbook). These are one programme rather than a set of unrelated items, and are listed in the order they should be taken — machinery first, then the doc that describes it, so the description is written once against a finished state rather than twice. Done so far: the permission and Auto mode review that led the list (D-260903b), the CI check on `.claude/` (D-260903c), linting each code file as it is written (D-260903d), moving the task-shaped procedures into skills (D-260904a), giving the validation set one entry point and one answer to "is this documentation-only?" (D-260904b), and settling the remaining advisory rules — branch names checked in CI, `git -C` in the hook, and the `-F`/`--body-file` rule demoted to advice once the hook stopped refusing prose (D-260904c), delegating the documentation sweep and the sensitive-information pass to subagents that cannot edit (D-260904d), having the release-ready check start a code review itself (D-260904e, since reversed), numbering that check's sequence with the commits inside it (D-260905b), and capping automatic subagent dispatch so the review is asked for rather than invoked ([2026-09-06](decisions/2026-09-06-cap-automatic-subagent-dispatch.md)) — the last three raised in conversation rather than by the playbook review, but part of the same programme and taken in the same order.

- [ ] **Give `.claude/` a topical doc.** No doc under `docs/` owns it: the hooks' rationale is spread across D-260814b, D-260903d and D-260904c, the permission posture is in D-260903b, the CI check in D-260903c, and the behaviour of all of it in `AGENTS.md`. Every one of those is now frozen in the [pre-migration archive](decisions/archive/2026-09-pre-migration.md), so the scatter is not reachable from any live document — which strengthens this item rather than dating it. What current behaviour there is under `docs/` sits in [Git hooks](development.md#git-hooks), which is a borrowed home — those are harness hooks, not git hooks, and the section says so in its own first line. That leaves the area without the topical home this project's own [documentation discipline](../AGENTS.md#documentation-discipline) asks for. The port collision this item used to carry is fixed rather than documented: the suite moved to 3002, giving one port per owner, and `yarn agent:check-config` asserts it. **Now due rather than optional**: `.claude/` holds four skills and two subagents as well as two hooks and a permission posture, and D-260904a made it a place procedures live rather than only configuration. The doc should say what each skill is for, when it triggers, and that a description is the whole trigger surface — the thing least obvious from reading the files. **What it was waiting for has landed**, which is why it is the last item here: D-260904d added the two review agents, D-260904e settled what the release-ready check runs, and D-260905b numbered that sequence and moved the commits into it — so the flow this doc would describe is now settled rather than about to change. Two things belong in its brief: the review is a bundled skill rather than anything in this directory, and is asked for rather than invoked, so nothing here dispatches it; and a skill's _prose_ is CI-asserted, which is a different claim from the frontmatter checks and easy to describe as though it were the same one. It must cover them too — what each reads, and why `tools: Glob, Grep, Read` is the guarantee rather than configuration, since an agent that cannot edit cannot resolve a finding instead of reporting it. Note that `tools` narrows where a skill's `allowed-tools` would widen; a doc that blurs the two would undo the distinction D-260904d exists to keep.

- [ ] **Decide which effort level to ask the code review for.** It has only ever been measured on a branch that was one script change and six documentation files — a floor rather than a representative diff — so whether the default finds enough on a change with real `src/` surface is unknown, and running it again on prose will not answer that. What changed is the cost side: the review is now run by a person in a fresh session rather than invoked from the release-ready check, so a higher effort level is paid for in that session alone and not in the working one, which makes this cheaper to answer than when it was first raised. The `postinstall`/`css-vars` item above is the natural carrier. Nothing to build; this is a measurement and a judgement.

- [ ] **Decide whether `meet.ouwl.house` should redirect from a public repository.** [`next.config.js`](../next.config.js) redirects it to a Google Meet room whose permanent code is committed in the clear. The code is not a credential and this is not a rotation; the question is the one the [sensitive-information pass](release-checklist.md#sensitive-information) asks of any third-party URL — what an anonymous caller can _do_ with it, rather than what they can read — and a meeting room is an entry point rather than a document. Raised by that pass on the D-260904e branch, which did not touch the file. The assessment itself belongs in the private maintainer runbook rather than here.

## Documentation weight

Raised by the proportionality audit of 2026-09-04, which compared the repository against `60bf27a`, the last human-maintained commit. Its finding: the executable machinery earns its keep on recorded evidence, and the prose around it does not. Of the 158 commits in that range, **143 touched `docs/` and 65 touched `src/`** — the site changed in 65 commits and the description of the site changed in 143. Retiring `project-history.md` was the first half; freezing the decision log into a directory of one file per decision was the second. What remains is the prose that audit could not see, because it counted files rather than reading them.

- [ ] **Give the monthly decision-log consolidation something that fires it.** [`docs/decisions/README.md`](decisions/README.md) says superseded and obsolete files move to `archive/` monthly, and nothing prompts that. A cadence with no trigger is a rule that does not run, and the first superseded decision is when that starts to cost something. Two candidate mechanisms, and they are not equivalent: a maintainer calendar reminder is what the Apple splash-device review already uses, recorded in [`pwa-seo.md`](pwa-seo.md), and it works because a person was going to do the judgement anyway; a scheduled GitHub Action is the only option that leaves a record in the repository, but it can at best open an issue or a pull request, because deciding what is obsolete is judgement rather than a query. Decide before the first supersede rather than after.

- [ ] **Bring the over-length comment blocks under the four-line limit.** The limit was set on 2026-09-06 without touching what already exceeds it. The backlog spans `e2e/`, `scripts/` and `src/`, the longest being the header of [`service-worker.spec.ts`](../e2e/service-worker.spec.ts), and [`global.css`](../src/styles/global.css) among the worst of them. **Measure before working from any figure.** The first count was wrong twice over: it matched only lines opening with `//` or `*`, so a CSS block comment's continuation lines ended the run and every `.css` file read as clean, and it counted blocks of six or more against a rule of four. That is what produced the original claim that the pressure had moved out of CSS and JSX — where the ban preceding this rule had put it — and the opposite is true. **Not all of them shrink.** The blocks in [`helpers.ts`](../e2e/support/helpers.ts) and [`accessibility.spec.ts`](../e2e/accessibility.spec.ts) explain what a check cannot see, which belongs in the topical doc beside that check rather than trimmed away — so this needs a destination decided per block, not a pass with a line counter. The documentation sweep now reports any it meets, so leaving this open means a standing finding on every change that touches those files, which is the pressure to do it rather than a reason to defer.

- [ ] **Fill the gaps in both script tables — `validate`, `branch:check` and `test:e2e:maps-smoke`.** The root [`README.md`](../README.md)'s table omits all three; [`development.md`](development.md#scripts-packagejson)'s has the first two and omits `test:e2e:maps-smoke`. `yarn validate` is the one that matters most — it is the entry point the whole [release sequence](release-checklist.md#before-opening-the-pr) turns on, and a reader working from the root table would not know it exists. Raised by the documentation sweep on D-260905b; pre-existing rather than caused by it.

## Code quality follow-ups

- [ ] **Replace `useIntersectedOnce` with `@mantine/hooks`' `useIntersection`.** The hand-rolled hook duplicates an IntersectionObserver wrapper the project already depends on. Not a drop-in swap: Mantine's hook exposes the raw `entry` on every change rather than latching once and disconnecting, so `MapWrapper` (its only consumer) would need to own that one-shot logic itself. Deferred deliberately rather than done alongside the D-260825e threshold fix, to keep that fix minimal.

- [ ] **Consider phonetic exceptions for `useArticleAgreement`'s vowel-sound check.** `vowelSoundPattern` matches the leading letter, not the leading sound, so a future tagline word like "European" or "MBA" would get the wrong article ("an European"). The current home-page word list doesn't trigger it, and the word list is fully author-controlled with every change subject to this repo's own preview-URL manual QA, so a wrong article would be caught immediately if it ever happened — deliberately left unfixed rather than building exceptions for words that don't exist in the sequence yet.

## Content & copy

- [ ] **Decide whether the experience-entry prose moves off its flat, factual register.** The job entries in `src/fixtures/experience.tsx` are uniformly declarative ("I joined X as a Y", "I worked in the team replacing…"), while the site's framing — the home bio, the page headers, the icon-only Flight Attendant entry — carries dry wit. Staying factual costs nothing to maintain and ages well, since enthusiasm is timestamped — the Equal Experts entry opened with an "excited to start this next chapter" line that was pared back to a plain statement for exactly that reason. Going conversational is a whole-history decision, not a per-entry one, or it leaves a visible seam around 2025. Middle path if revisited: keep entries factual and past-tense by default, allow one voice sentence per entry only where there is a genuine story (the CSA no-prior-Python line is the model), and decide the seam explicitly. Raised during the 2026-08-29 copy pass and deliberately not acted on.
