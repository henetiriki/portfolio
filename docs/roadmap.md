Whole-project coverage went from ~0% to ~84%. `components/travel` (`Map`, `Marker`, `Polyline`, `MapWrapper`) — the highest-effort tier by far — landed at 93.6% stmts / 87.7% branch via a hand-built `google.maps` SDK mock (`src/utils/test/googleMapsMock.ts`); see [development.md](development.md#testing) for the full set of mocking patterns this required. The Maps-layer tests were written _after_ fixing the two regressions found below, per the original sequencing plan (encode intended behavior, not whatever the buggy code happened to do).
- [x] **Add a CI workflow.** Done 2026-08-06 — [.github/workflows/ci.yml](../.github/workflows/ci.yml) runs lint, type-check, format check, and `test:coverage` on PRs to `main` and pushes to `main`. No secrets needed (`.env.test` covers config validation). Not yet blocking anything — see below.
- [ ] **Enforce coverage thresholds & block merges on it.** Coverage work is now done (~84% whole-project, see above), so a global `coverageThreshold` in `jest.config.js` is realistic to turn on today — that part just needs picking back up. Goal: ≥80% overall, and PRs blocked if _new/changed_ code isn't at 80% (diff/patch coverage, not just a global number). Two open decisions to make when this is picked back up:
  - **Global 80% threshold**: turn on all at once once we're near it, or ratchet a lower `coverageThreshold` up incrementally as tiers land?
  - **Diff/patch coverage on new code**: Jest's `coverageThreshold` can't do this natively (whole-file/global only). Real options are Codecov/Coveralls (industry standard for this, but the repo is private so it needs a `CODECOV_TOKEN` — requires creating/connecting an account, which is a step for a human, not something to script) vs. a self-hosted diff-coverage action (no external account, but less battle-tested).
  - Either way, actually _blocking_ merges requires a branch protection rule on `main` requiring the check — a real repo-settings change to confirm explicitly when we get there, separate from building the check itself.

## Bug fixes

- [x] **Audit & fix the Google Maps layer regressions.** Done 2026-08-06. Code-reading audit (comparing `Marker`'s and `Polyline`'s call sites in `MapWrapper.tsx`) turned up two confirmed regressions from the vanilla-JS→React port:
  - **Marker drop-in staggering was broken.** `Marker`/`Polyline` both stagger their drop-in animation via `cancelableDelay(idx * order * 100, ...)` — a multiplication, so `idx === 0` always produces a `0` delay regardless of `order`. `Polyline`'s call sites already dodged this (`idx + 1`); `Marker`'s didn't, so the first airport/station/port marker in each group dropped simultaneously instead of staggering. Fixed in `MapWrapper.tsx` by passing `idx + 1` to `Marker`, matching `Polyline`'s existing pattern.
  - **Zoom reset on resize.** `Map.tsx`'s viewport-size effect forced `zoom` back to the breakpoint default on every `width` change, not just initial mount — so resizing the window after the map loaded would silently discard the user's manual zoom. Fixed by tracking initial setup with a ref (`initialZoomSetRef`) so only `minZoom` stays reactive to viewport width after the first render; `zoom` is set once.
  - Both fixes are covered by regression tests in `components/travel/__tests__/` (`Map.test.tsx`'s "does not force zoom again on a later resize", `MapWrapper.test.tsx`'s "never passes idx=0 to a marker").
