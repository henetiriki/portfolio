# Roadmap

Open work only. A completed item is simply removed — the merged pull request is the record that it happened, and current behaviour goes to the topical documentation. Items are grouped by area rather than strict priority; each should normally be delivered as its own scoped change unless a dependency is called out explicitly.

Last reviewed: 2026-09-07.

## Framework & dependency upgrades

- [ ] **Adopt the native TypeScript 7 toolchain when ecosystem support is ready — blocked.** The project now uses TypeScript 6, the supported JavaScript-based bridge release, with its configuration deprecations already removed. The 2026-08-09 TypeScript `7.0.2` trial still failed before compilation because Yarn's built-in compatibility patch expected `lib/_tsc.js`, which the native Go distribution does not ship; `typescript-eslint` also still declares a `typescript` peer range below `6.1.0` (checked through 8.69, 2026-09-03). Recheck only when Yarn supports the native distribution and TypeScript-ESLint supports its compiler API strategy; both conditions are required.

- [ ] **Upgrade Babel 7 to 8 when Jest supports it — blocked.** The app compiles with SWC and has no Babel configuration; Babel is a direct development dependency solely for Jest. `jest-config`, `@jest/transform` and `jest-snapshot` still depend on Babel 7, so follow Jest's support rather than forcing an app-irrelevant major ahead of its consumer.

- [ ] **Upgrade Node.js 24 to 26 on or after 2026-10-28.** The project follows Active LTS releases, and Node 26 does not reach that status until then. Confirm Vercel support first, then update `engines.node`, `.nvmrc` and `@types/node` together and validate installation, native dependencies, the full suite and both build modes on the new runtime.

- [ ] **Drop the `@serwist/next/browserslist` resolution once the upstream pin moves.** `package.json` carries a `resolutions` entry forcing `^4.28.7` because `@serwist/next` pins `browserslist` to the vulnerable `4.28.6` exactly, and its latest release still does. Check it at the next `@serwist/next` upgrade: if the published `dependencies` block names anything `4.28.7` or later, remove the entry, run `yarn install` and confirm `yarn npm audit --all --recursive` stays clean. An override left behind after upstream has moved is worse than none — it pins the graph to a range nobody is watching any more.

## CI & security hardening

- [ ] **Decide what `update-visual-baselines.yml` does with a `dependabot/` branch, and record the answer where the guard is.** Its `Validate target branch` step carries a second, independent copy of the prefix allowlist — `feature/*|fix/*|docs/*|chore/*` in a `case` — which now disagrees with the [branch-name check](../AGENTS.md#branch-names) after `dependabot/` was added there. The concrete case is a bump that shifts rendering: the baseline update cannot be run on the Dependabot ref, and the job aborts saying the branch must use a repository branch prefix, which it does. **Both answers are defensible and that is why this is not a one-line fix.** Adding the prefix widens what a job holding `contents: write` may push to, onto a branch Dependabot itself force-pushes when it rebases; leaving it out means rebasing the bump onto a `chore/` branch to regenerate, which is a workable manual route. Whichever it is, the guard should say why in a comment, because the next reader will otherwise read the disagreement as drift. Raised by the code review on the branch that added the prefix.

- [ ] **Upgrade ESLint off `9.39.5`.** `yarn npm audit --all` flags it as a deprecated, no-longer-supported version (moderate severity); it's a development-only dependency so there's no production exposure, but it's currently excluded from Dependabot's automated major-version updates (see `.github/dependabot.yml`'s `ignore` list) pending a coordinated config/plugin compatibility pass.

## Agent configuration

- [ ] **Decide which effort level to ask the code review for.** It has only ever been measured on a branch that was one script change and six documentation files — a floor rather than a representative diff — so whether the default finds enough on a change with real `src/` surface is unknown, and running it again on prose will not answer that. What changed is the cost side: the review is now run by a person in a fresh session rather than invoked from the release-ready check, so a higher effort level is paid for in that session alone and not in the working one, which makes this cheaper to answer than when it was first raised. The `postinstall`/`css-vars` change was named as the carrier and did not serve as one: it landed as a single script edit plus documentation, the same shape as the floor. The carrier has to be a change with real `src/` surface. Nothing to build; this is a measurement and a judgement.

- [ ] **Decide whether `meet.ouwl.house` should redirect from a public repository.** [`next.config.js`](../next.config.js) redirects it to a Google Meet room whose permanent code is committed in the clear. The code is not a credential and this is not a rotation; the question is the one the [sensitive-information pass](release-checklist.md#sensitive-information) asks of any third-party URL — what an anonymous caller can _do_ with it, rather than what they can read — and a meeting room is an entry point rather than a document. Raised by that pass on an earlier branch, which did not touch the file. The assessment itself belongs in the private maintainer runbook rather than here.

- [ ] **Verify a recognised provider key is already blocked at push time via secret scanning and push protection, and check whether `secret_scanning_non_provider_patterns` is enabled** — it is the half that catches what no provider format matches. Verify the live state before acting on this.

## Documentation weight

Raised by the proportionality audit of 2026-09-04, which compared the repository against `60bf27a`, the last human-maintained commit. Its finding: the executable machinery earns its keep on recorded evidence, and the prose around it does not. Of the 158 commits in that range, **143 touched `docs/` and 65 touched `src/`** — the site changed in 65 commits and the description of the site changed in 143. Retiring `project-history.md` was the first half; freezing the decision log into a directory of one file per decision was the second. What remains is the prose that audit could not see, because it counted files rather than reading them.

- [ ] **Bring the over-length comment blocks under the four-line limit.** The limit was set on 2026-09-06 without touching what already exceeds it. The backlog spans `e2e/`, `scripts/` and `src/`, the longest being the header of [`service-worker.spec.ts`](../e2e/service-worker.spec.ts), and [`global.css`](../src/styles/global.css) among the worst of them. **It also spans the root config files and `.github/`, which that list originally omitted** — the `workers` comment in [`playwright.config.ts`](../playwright.config.ts) and the Playwright-cache comments in [`ci.yml`](../.github/workflows/ci.yml) both exceed the limit, and the documentation sweep of 2026-09-06 raised the cost of leaving them: `development.md` now delegates to both rather than restating them, so they are the authoritative copy. **`ci.yml`'s share is wider than the Playwright-cache comments named above** — the `classify` job header, the branch-name step's seven-line block and the `agent:check-config` one all exceed it too, so treat the file as a sweep rather than two known blocks. The `workers` one also carries a drifting spec count. **Measure before working from any figure.** The first count was wrong twice over: it matched only lines opening with `//` or `*`, so a CSS block comment's continuation lines ended the run and every `.css` file read as clean, and it counted blocks of six or more against a rule of four. That is what produced the original claim that the pressure had moved out of CSS and JSX — where the ban preceding this rule had put it — and the opposite is true. **Not all of them shrink.** The blocks in [`helpers.ts`](../e2e/support/helpers.ts) and [`accessibility.spec.ts`](../e2e/accessibility.spec.ts) explain what a check cannot see, which belongs in the topical doc beside that check rather than trimmed away — so this needs a destination decided per block, not a pass with a line counter. The documentation sweep now reports any it meets, so leaving this open means a standing finding on every change that touches those files, which is the pressure to do it rather than a reason to defer.

## Documentation gaps

- [ ] **Record when a repository setting may be named publicly — blocked on a maintainer check.** The [sensitive-information section](release-checklist.md#sensitive-information) asks whether a new third-party URL is safe to publish, but says nothing about configuration values, and `squash_merge_commit_message` is named in two public files without a rule to point at. The line proposed by the pass that cleared it: a setting is public-safe where its value is observable from outside and carries no security function, and belongs in the private runbook where it names a protection's exact configuration, an exemption, who can bypass it, or what is not monitored. That reasoning holds for this one — its effect is visible in every squash commit on public `main`, and withholding it while publicly documenting squash-only merging and the ruleset's no-bypass-actors posture would be incoherent. **Blocked because it assumes the runbook has no blanket rule making configuration values private as a class**, which is not inferable from anything public; confirm that before writing the bullet, and move the two existing mentions if it turns out otherwise.

- [ ] **Fill the gaps in both script tables — `validate`, `branch:check` and `test:e2e:maps-smoke`.** The root [`README.md`](../README.md)'s table omits all three; [`development.md`](development.md#scripts-packagejson)'s has the first two and omits `test:e2e:maps-smoke`. `yarn validate` is the one that matters most — it is the entry point the whole [release sequence](release-checklist.md#before-opening-the-pr) turns on, and a reader working from the root table would not know it exists. Raised by a documentation sweep; pre-existing rather than caused by it.

## Code quality follow-ups

- [ ] **Replace `useIntersectedOnce` with `@mantine/hooks`' `useIntersection`.** The hand-rolled hook duplicates an IntersectionObserver wrapper the project already depends on. Not a drop-in swap: Mantine's hook exposes the raw `entry` on every change rather than latching once and disconnecting, so `MapWrapper` (its only consumer) would need to own that one-shot logic itself. Deferred deliberately rather than done alongside the threshold fix that raised it, to keep that fix minimal.

- [ ] **Consider phonetic exceptions for `useArticleAgreement`'s vowel-sound check.** `vowelSoundPattern` matches the leading letter, not the leading sound, so a future tagline word like "European" or "MBA" would get the wrong article ("an European"). The current home-page word list doesn't trigger it, and the word list is fully author-controlled with every change subject to this repo's own preview-URL manual QA, so a wrong article would be caught immediately if it ever happened — deliberately left unfixed rather than building exceptions for words that don't exist in the sequence yet.

## Content & copy

- [ ] **Decide whether the experience-entry prose moves off its flat, factual register.** The job entries in `src/fixtures/experience.tsx` are uniformly declarative ("I joined X as a Y", "I worked in the team replacing…"), while the site's framing — the home bio, the page headers, the icon-only Flight Attendant entry — carries dry wit. Staying factual costs nothing to maintain and ages well, since enthusiasm is timestamped — the Equal Experts entry opened with an "excited to start this next chapter" line that was pared back to a plain statement for exactly that reason. Going conversational is a whole-history decision, not a per-entry one, or it leaves a visible seam around 2025. Middle path if revisited: keep entries factual and past-tense by default, allow one voice sentence per entry only where there is a genuine story (the CSA no-prior-Python line is the model), and decide the seam explicitly. Raised during the 2026-08-29 copy pass and deliberately not acted on.

## Performance, SEO & platform polish

- [ ] **Confirm the white band behind the Android gesture bar clears once Chrome stable ships the upstream fix.** Nothing to build — the fix merged into Chromium `main` on 2026-08-06 and colours the navigation bar from `theme_color`, already correct here.
  - **Earliest realistic check is late September 2026**, since `main` reaches stable in roughly four to ten weeks. Install the app on Android and confirm the region behind the gesture bar is `#080a20`.
  - **If it has not cleared by then, check the killswitch before rebuilding a workaround.** The fix ships behind `WebAppNavigationBarThemeColor`, default-on — a disabled or reverted flag would look identical to no fix at all.
