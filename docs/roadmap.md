# Roadmap

Open work only. Completed milestones are recorded in [Project History](project-history.md), durable rationale in [Engineering Decisions](decisions.md), and current behaviour in the topical documentation. Items are grouped by area rather than strict priority; each should normally be delivered as its own scoped change unless a dependency is called out explicitly.

Last reviewed: 2026-08-15.

## Testing & automation

- [ ] **Enforce required checks on `main` — waiting on repository visibility, not on configuration.** CI uploads Jest's explicit LCOV report to Codecov through short-lived GitHub OIDC authentication, with a strict 100% patch target and source-line annotations. Reporting works; blocking does not, and cannot yet.
  - **This is not a settings toggle.** Verified 2026-08-11: both the classic branch-protection API and the newer rulesets API return `403 Upgrade to GitHub Pro or make this repository public to enable this feature`. Required status checks are unavailable for a private repository on a free personal plan, so no amount of repository configuration will enable them.
  - **Decision: make the repository public once the remaining actionable roadmap items are done**, then require both `CI / Validate & build` and `codecov/patch` on `main`. Publishing is preferred over a paid plan for a personal portfolio site whose source is not sensitive.
  - **Before publishing**, enable Cloudinary's **strict transformations** and restrict `fetch` delivery. The cloud name is unavoidably public — it appears in every delivery URL and is already inlined in the shipped client bundle — so anyone can request arbitrary on-the-fly transformations and burn transformation credits. That exposure exists today; publishing simply makes the account easier to notice. This is a billing-abuse control, not a data-exposure one.
  - **Also before publishing**, confirm the repository history carries no secrets. `.env` and `.env.test` are tracked but hold only non-secret or dummy values; real credentials live in `.env*.local`, which is gitignored. That is the current state — history should still be checked rather than assumed, because publishing exposes every past commit, not just the tip.
  - **The check names here are not stable.** The item below splits `CI / Validate & build` into two jobs once the repository is public. Whichever lands second owns updating branch protection, because a rule requiring a check that no longer runs blocks every pull request indefinitely.

- [ ] **Split the browser suite into its own CI job — after the repository is public, not before.** [`ci.yml`](../.github/workflows/ci.yml) runs everything in one serial `Validate & build` job, so lint, types, formatting and unit tests all wait behind a production build, a Playwright browser download and the browser suite. The two halves are independent and could run concurrently.
  - **The split.** One job for install → `css-vars:check` → lint → type-check (application and service worker) → `prettier:check` → `test:coverage` → Codecov upload. Another for install → `build` → `test -s public/sw.js` → Playwright install → `test:e2e`. Nothing in the first feeds the second: the fast checks all run against source, and only the browser suite needs `.next`, because Playwright's `webServer` starts `yarn start`. The Next build cache belongs solely to the second job, so the two do not contend for it either.
  - **Why it waits for publication, rather than being done now.** Two parallel jobs each pay their own `yarn install`, and while the repository is private those minutes bill against the free monthly allowance. August 2026 usage was already around 70% of that allowance by the 14th — gross rather than billed, but on that trajectory. Public repositories get unmetered Actions minutes, which turns this from a trade of money for latency into a straight win.
  - **Hoist the `env:` block to workflow level first.** The build needs all fifteen variables, so a naive split duplicates the block across both jobs, and the next person to add a variable will update only one copy.
  - **Splitting renames the required check**, replacing `CI / Validate & build` with two. See the coupling noted on the item above.

- [ ] **Stop running the production build and browser suite on documentation-only changes — actionable now, unlike the split above.** [`vercel.json`](../vercel.json) already skips the deploy when a change touches only `docs/`, `*.md`, `.claude/`, `.worktreeinclude`, `e2e/` or `playwright.config.ts`, on the reasoning that nothing it changes can reach a visitor. CI has no equivalent, so a roadmap edit still pays for a production build, a Playwright browser download and the whole browser suite. This project is deliberately documentation-heavy — the [release checklist](release-checklist.md#documentation-sweep) makes a docs sweep part of every change, and several recent pull requests were documentation only — so this is a recurring cost, not an occasional one. #167 alone ran it four times, three of them for prose.
  - **Do not skip the run wholesale.** `prettier:check` runs `prettier .` across the tree, so Markdown and JSON _are_ checked, and on a documentation-only change it is the only check that applies to what changed. A blanket skip would remove the one thing still worth running. `eslint` and both type-checks cover no Markdown, and Jest cannot be affected by it.
  - **So the shape is a cheap path, not an absent one**: install and `prettier:check`, skipping `build`, the Playwright install, `test:e2e` and the Jest run. That keeps the formatting guarantee while dropping nearly all of the cost.
  - **`paths-ignore` is the wrong mechanism and will bite later.** A workflow filtered out that way never reports, and a _required_ check that never reports leaves a pull request pending forever — so it would silently break the branch protection the first item plans. Filter inside the job instead, so the check still runs and still reports success.
  - **Match the exclusions to CI's question, not Vercel's.** Vercel asks whether a change can reach a visitor; CI asks whether it can affect lint, types, tests or the build. **The two lists have now actually diverged**, so this is no longer a hypothetical: `e2e/` and `playwright.config.ts` were added to Vercel's exclusions on 2026-08-15, and they are precisely the paths whose change _must_ run the full browser suite. Copying Vercel's list into CI would skip the suite exactly when it is the only thing that could catch the change.

- [ ] **Extend the browser regression suite.** The harness and its first specs have landed — see [Development Workflow](development.md#browser-regression-suite). Remaining candidates, still deliberately narrow:
  - Consider a reduced-motion pass (`prefers-reduced-motion`), since the map reveal, marker drop and smooth scrolling all branch on it. Playwright can set it per project via `use.reducedMotion`, so this is a project variant rather than new specs.
  - Consider covering the footer's own scroll-to-top control, which shares `pageTopRef` with the header's but has a separate call site.

- [ ] **Decide whether the duplicated maskable icons should be a separate `purpose: any` set.** `public/manifest.json` declares four icon entries but only two files exist — `manifest-icon-192.maskable.png` and `manifest-icon-512.maskable.png`, each listed twice, once as `purpose: any` and once as `maskable`. That satisfies Chrome's requirement and installability is fine, so this is cosmetic: a maskable image used as `any` carries its own safe-zone padding and therefore renders inset wherever the platform expects full-bleed. Noted because it is deliberate-looking duplication a tidy-up could easily break — and the browser suite now asserts the 192/512 `any` pair, so removing the duplicates without adding real `any` files will fail rather than ship.

## Framework & dependency upgrades

- [ ] **Adopt the native TypeScript 7 toolchain when ecosystem support is ready — blocked.** The project now uses TypeScript 6, the supported JavaScript-based bridge release, with its configuration deprecations already removed. The 2026-08-09 TypeScript `7.0.2` trial still failed before compilation because Yarn's built-in compatibility patch expected `lib/_tsc.js`, which the native Go distribution does not ship; `typescript-eslint@8.66` also requires TypeScript `<6.1.0`. Recheck only when Yarn supports the native distribution and TypeScript-ESLint supports its compiler API strategy; both conditions are required.

- [ ] **Upgrade Babel 7 to 8 when Jest supports it — blocked.** The app compiles with SWC and has no Babel configuration; Babel is a direct development dependency solely for Jest. `jest-config`, `@jest/transform` and `jest-snapshot` still depend on Babel 7, so follow Jest's support rather than forcing an app-irrelevant major ahead of its consumer.

- [ ] **Upgrade Node.js 24 to 26 on or after 2026-10-28.** The project follows Active LTS releases, and Node 26 does not reach that status until then. Confirm Vercel support first, then update `engines.node`, `.nvmrc` and `@types/node` together and validate installation, native dependencies, the full suite and both build modes on the new runtime. See [D-260806a](decisions.md#d-260806a--track-active-lts-nodejs-releases).

## Performance, SEO & platform polish

- [ ] **Promote the Content Security Policy from Report-Only to enforcing.** The policy, the report endpoint and its browser coverage have landed — see [Security](security.md#content-security-policy) and [D-260814c](decisions.md#d-260814c--ship-the-content-security-policy-report-only-and-accept-unsafe-inline). What remains is the judgement call the Report-Only phase exists to inform.
  - **Read the reports, not the console.** `/api/csp-report` logs one line per violation to the Vercel runtime logs, with extension noise already filtered. The console is specifically not the signal: a Maps `gen_204?csp_test=true` probe on `/travel` already fails as `ERR_BLOCKED_BY_CLIENT` for client-side blockers with no policy deployed at all, so a blocked probe cannot distinguish our header from the visitor's blocker. That single error is also the entire reason `/travel` scores **Best Practices 96**, and it must not later be misread as CSP fallout.
  - **The reports expire, so switch the emailing on before opening a window.** Vercel's runtime logs are a rolling buffer measured in hours to days, not the weeks this decision needs. Setting `CSP_VIOLATION_EMAILS=true` and redeploying makes them durable — see [Security](security.md#emailing-violations-temporary) — and switching it back off is part of closing the window, along with deleting `src/server/csp-mail/`.
  - **Promote the safe half now, rather than waiting on the allowlist.** `frame-ancestors`, `base-uri`, `form-action` and `object-src 'none'` do not depend on any allowlist being complete, and no report can change whether they are correct. Ship those as an enforcing `Content-Security-Policy` alongside the Report-Only header — both are valid together and browsers apply each independently — and keep only the resource directives under observation.
  - **"Clean" has to mean covered, not just quiet.** Zero reports prove nothing if the path never ran. Still unexercised: `/travel` with Maps genuinely loading, `/experience` with the YouTube embed actually playing, and `/contact` with a real submission (BotID loads `p.js` on demand and may pull hosts the passive path does not).
    - **Service-worker registration is no longer on that list.** `service-worker.spec.ts` now runs it under the deployed policy and produces no violation, so `worker-src 'self' blob:` has evidence behind it for the first time — see [D-260815a](decisions.md#d-260815a--give-the-service-worker-its-own-playwright-project-rather-than-unblocking-it-everywhere). Note the evidence is local and Chromium-only, so it does not discharge the cross-engine requirement below.
  - **Two allowlist gaps are already known, both on `/travel`, both from Google Maps.** Found 2026-08-14 under `next dev` in a worktree, driving Playwright's Chromium over `/`, `/experience`, `/contact` and `/travel`; the other three pages produced no violation at all. Neither is a development artefact — both come from the Maps SDK itself and should be expected in production, but confirm them against real reports rather than promoting on this evidence alone.
    - Maps **compiles a WebAssembly module**, which `script-src` refuses for want of `'unsafe-eval'`. Prefer `'wasm-unsafe-eval'`, which permits exactly this and nothing else; `'unsafe-eval'` would be a far wider grant than the violation calls for.
    - Maps connects to **`https://mapsresources-pa.googleapis.com`** for style tables, which `connect-src` does not list. Note `img-src` already carries `https://*.googleapis.com` while `connect-src` names only `maps.googleapis.com` — the gap is that narrowness, not a missing wildcard.
  - **Turbopack is not a violator, which removes one open question.** The concern that its HMR runtime would need `'unsafe-eval'` and flood development with noise was checked in the same run and is unfounded — it produced nothing.
  - **It must include Safari and Firefox.** An allowlist tuned on Chrome-only reports is a known way to ship a policy that breaks elsewhere: the three engines name directives differently and Safari reports things Chrome does not.
  - **Promotion is a one-line change** — the header key in `next.config.js` — plus deleting the assertion in `security-headers.spec.ts` that the enforcing header is absent. Keep `report-uri` afterwards; an enforcing policy needs reports more than a Report-Only one does.
  - **Two Google Fonts entries are candidates for removal, and must be checked rather than assumed.** `font-src` still names `https://fonts.gstatic.com` and `style-src` still names `https://fonts.googleapis.com`, both left from before the fonts were vendored on 2026-08-14 ([D-260814a](decisions.md#d-260814a--vendor-what-the-build-cannot-proceed-without)). What is verified is only that nothing under `src/`, `service-worker/` or `public/` references either host — which does **not** establish that nothing requests them, because a third-party SDK loads what this repository never mentions. The Maps SDK is the specific suspect: it has historically injected a `fonts.googleapis.com` Roboto stylesheet for its own controls, and `/travel` is the one page nothing here has observed with Maps genuinely loading. Confirm against a real page load before removing either, then remove them under Report-Only where a wrong answer is a report rather than a missing font.
  - **Do not treat `'unsafe-inline'` as the thing to remove first.** It is permanent while BotID renders a nonce-less inline script and every page is statically prerendered ([D-260814c](decisions.md#d-260814c--ship-the-content-security-policy-report-only-and-accept-unsafe-inline)). Removing it is a separate, much larger question about whether these pages should render per request at all.
