# Roadmap

Open work only. Completed milestones are recorded in [Project History](project-history.md), durable rationale in [Engineering Decisions](decisions.md), and current behaviour in the topical documentation. Items are grouped by area rather than strict priority; each should normally be delivered as its own scoped change unless a dependency is called out explicitly.

Last reviewed: 2026-08-15.

## Testing & automation

- [ ] **Enforce required checks on `main` — waiting on repository visibility, not on configuration.** CI uploads Jest's explicit LCOV report to Codecov through short-lived GitHub OIDC authentication, with a strict 100% patch target and source-line annotations. Reporting works; blocking does not, and cannot yet.
  - **This is not a settings toggle.** Verified 2026-08-11: both the classic branch-protection API and the newer rulesets API return `403 Upgrade to GitHub Pro or make this repository public to enable this feature`. Required status checks are unavailable for a private repository on a free personal plan, so no amount of repository configuration will enable them.
  - **Decision: make the repository public once the remaining actionable roadmap items are done**, then require both `CI / Validate & build` and `codecov/patch` on `main`. Publishing is preferred over a paid plan for a personal portfolio site whose source is not sensitive.
  - **Before publishing**, enable Cloudinary's **strict transformations** and restrict `fetch` delivery. The cloud name is unavoidably public — it appears in every delivery URL and is already inlined in the shipped client bundle — so anyone can request arbitrary on-the-fly transformations and burn transformation credits. That exposure exists today; publishing simply makes the account easier to notice. This is a billing-abuse control, not a data-exposure one.
  - **Also before publishing**, confirm the repository history carries no secrets. `.env` and `.env.test` are tracked but hold only non-secret or dummy values; real credentials live in `.env*.local`, which is gitignored. That is the current state — history should still be checked rather than assumed, because publishing exposes every past commit, not just the tip.
  - **The check names here are not stable.** The item below splits `CI / Validate & build` into two jobs once the repository is public. Whichever lands second owns updating branch protection, because a rule requiring a check that no longer runs blocks every pull request indefinitely.
  - **Restore the Jest run and the Codecov upload to CI's [cheap path](release-checklist.md#pull-request) as part of publishing, before the rule is applied.** That path currently skips both on a documentation-only change, so nothing is uploaded and Codecov is not expected to post a status at all — which would leave a required `codecov/patch` pending forever, the exact failure `paths-ignore` was rejected for in [D-260815c](decisions.md#d-260815c--give-documentation-only-changes-a-cheap-ci-path-rather-than-no-ci-run). **Decided 2026-08-15: put them back rather than drop the requirement.** Jest is the fast part of what the path skips — 308 tests in under four seconds locally — so it costs a few percent of the saving and removes the edge case instead of betting on Codecov's behaviour with no upload. Two `if:` lines in `ci.yml`, plus the paragraphs describing the skip. Harmless to leave as-is until then: no check is required today, so a missing status blocks nothing.

- [ ] **Split the browser suite into its own CI job — after the repository is public, not before.** [`ci.yml`](../.github/workflows/ci.yml) runs everything in one serial `Validate & build` job, so lint, types, formatting and unit tests all wait behind a production build, a Playwright browser download and the browser suite. The two halves are independent and could run concurrently.
  - **The split.** One job for install → `css-vars:check` → lint → type-check (application and service worker) → `prettier:check` → `test:coverage` → Codecov upload. Another for install → `build` → `test -s public/sw.js` → Playwright install → `test:e2e`. Nothing in the first feeds the second: the fast checks all run against source, and only the browser suite needs `.next`, because Playwright's `webServer` starts `yarn start`. The Next build cache belongs solely to the second job, so the two do not contend for it either.
  - **Why it waits for publication, rather than being done now.** Two parallel jobs each pay their own `yarn install`, and while the repository is private those minutes bill against the free monthly allowance. August 2026 usage was already around 70% of that allowance by the 14th — gross rather than billed, but on that trajectory. Public repositories get unmetered Actions minutes, which turns this from a trade of money for latency into a straight win.
  - **Hoist the `env:` block to workflow level first.** The build needs all fifteen variables, so a naive split duplicates the block across both jobs, and the next person to add a variable will update only one copy.
  - **The split subsumes half of the documentation-only cheap path.** The second job _is_ everything that path skips, so it becomes one `if:` on the job rather than a gate per step; the classification has to move to its own small job whose output both consume, since `steps.*` does not cross jobs. See [D-260815c](decisions.md#d-260815c--give-documentation-only-changes-a-cheap-ci-path-rather-than-no-ci-run). The first job keeps per-step gates, because `prettier:check` — and, once restored per the item above, the Jest run and Codecov upload — still runs when the rest of it does not.
  - **Splitting renames the required check**, replacing `CI / Validate & build` with two. See the coupling noted on the item above.

- [ ] **Extend the browser regression suite.** The harness and its first specs have landed — see [Development Workflow](development.md#browser-regression-suite). Remaining candidates, still deliberately narrow:
  - Consider a reduced-motion pass (`prefers-reduced-motion`), since the map reveal, marker drop and smooth scrolling all branch on it. Playwright can set it per project via `use.reducedMotion`, so this is a project variant rather than new specs.
  - Consider covering the footer's own scroll-to-top control, which shares `pageTopRef` with the header's but has a separate call site.

## Framework & dependency upgrades

- [ ] **Adopt the native TypeScript 7 toolchain when ecosystem support is ready — blocked.** The project now uses TypeScript 6, the supported JavaScript-based bridge release, with its configuration deprecations already removed. The 2026-08-09 TypeScript `7.0.2` trial still failed before compilation because Yarn's built-in compatibility patch expected `lib/_tsc.js`, which the native Go distribution does not ship; `typescript-eslint@8.66` also requires TypeScript `<6.1.0`. Recheck only when Yarn supports the native distribution and TypeScript-ESLint supports its compiler API strategy; both conditions are required.

- [ ] **Upgrade Babel 7 to 8 when Jest supports it — blocked.** The app compiles with SWC and has no Babel configuration; Babel is a direct development dependency solely for Jest. `jest-config`, `@jest/transform` and `jest-snapshot` still depend on Babel 7, so follow Jest's support rather than forcing an app-irrelevant major ahead of its consumer.

- [ ] **Upgrade Node.js 24 to 26 on or after 2026-10-28.** The project follows Active LTS releases, and Node 26 does not reach that status until then. Confirm Vercel support first, then update `engines.node`, `.nvmrc` and `@types/node` together and validate installation, native dependencies, the full suite and both build modes on the new runtime. See [D-260806a](decisions.md#d-260806a--track-active-lts-nodejs-releases).

## Performance, SEO & platform polish

- [ ] **Confirm the white band behind the Android gesture bar clears once Chrome stable ships the upstream fix.** Nothing to build — the fix merged into Chromium `main` on 2026-08-06 and colours the navigation bar from `theme_color`, already correct here. See [D-260816a](decisions.md#d-260816a--wait-for-the-chromium-fix-instead-of-working-around-the-android-navigation-bar).
  - **Earliest realistic check is late September 2026**, since `main` reaches stable in roughly four to ten weeks. Install the app on Android and confirm the region behind the gesture bar is `#080a20`.
  - **If it has not cleared by then, check the killswitch before rebuilding a workaround.** The fix ships behind `WebAppNavigationBarThemeColor`, default-on — a disabled or reverted flag would look identical to no fix at all.
  - **Two workarounds already exist and were discarded deliberately**, so neither needs rediscovering: reverting `display` to `fullscreen` (one word, costs the Android status bar permanently, iOS unaffected) and `viewport-fit=cover` (needs `env(safe-area-inset-*)` on the sticky header, the fixed scroll-to-top control, the footer's bottom band and the full-screen mobile drawer — the drawer least certain, since its close button is absolutely positioned and it could not be opened under browser automation to verify).

- [ ] **Keep the splash matrix from going stale again, and stop precaching all of it.** The set is correct as of 2026-08-15 ([D-260815e](decisions.md#d-260815e--generate-the-pwa-icon-and-splash-set-from-one-vector-master)), but nothing keeps it that way and two follow-ups are worth taking together.
  - **Every new Apple device silently loses its splash.** A class with no `apple-touch-startup-image` entry gets nothing, with no warning — the previous set missed four years of hardware before anyone noticed. Regenerating is now a script run, so the open question is what prompts it: a check that fails when a known device class is unmatched beats remembering each September.
  - **All 42 splash images are precached by Serwist** because they sit in `public/` — roughly 2 MB into every installed app to use at most two files. Excluding them from the precache manifest is the obvious win, since the OS fetches them at launch rather than the page, but confirm the launch screen still appears offline before assuming it.
  - **The generator is not in the repository.** It ran from a scratch directory, so the assets are reproducible only by rewriting it. Committing it, and the device table it encodes, is what would make both items above cheap.

- [ ] **Correct the stated location: the site still says Wellington, New Zealand.** Louw is now based on the Garden Route, South Africa, and two pieces of prose contradict that. Agreed 2026-08-15.
  - **Exactly two call sites, both on the home page**, confirmed by a search across `src/`, `public/` and `docs/`: the SEO description at [`index.tsx:19`](../src/pages/index.tsx) ("a front-end engineer based in Wellington, New Zealand") and the hero subtitle at [`index.tsx:66`](../src/pages/index.tsx) (`Front-end Engineer, Wellington NZ`). The description is the one that matters most — it is the meta description, the Open Graph description and the social card text for the site's root URL.
  - **Do not touch `src/fixtures/experience.tsx`.** Its nine `Wellington, New Zealand` values are the locations of past roles, which remain true and would become wrong if updated.
  - **The travel map is already correct** and needs nothing: the `current: true` city fixture is Mossel Bay, moved there when the vector map landed. That the map and the prose disagree today is the defect.
  - **Decide how specific the replacement should be** — "Garden Route, South Africa" reads naturally and matches the map's granularity; a town name would be more precise but pins a home address on a public page, which the current wording deliberately does not.
  - Check `public/llms.txt` in the same pass. It carries no location today, but it is the kind of file that acquires one.
  - **The build timestamp is still New Zealand too, and belongs in this change.** `lastModified` in [`next.config.js`](../next.config.js) formats with `en-NZ` and `timeZone: 'Pacific/Auckland'`; it should be `en-ZA` and `Africa/Johannesburg`. It feeds `NEXT_PUBLIC_LAST_MODIFIED`, which is the footer's "Updated:" value, so the visible effect is a deploy timestamp reading in the reader's — and the owner's — actual timezone. Agreed 2026-08-15.
    - Both locales format day-first with a 24-hour clock, so the shape of the string does not change; `timeZoneName: 'short'` is what visibly moves, from `NZST`/`NZDT` to `SAST`. South Africa observes no daylight saving, so the abbreviation stops alternating.
    - `NEXT_PUBLIC_LAST_MODIFIED` is also the precache revision for `/_offline` ([D-260815g](decisions.md#d-260815g--precache-the-offline-document-which-the-build-manifest-omits)). Changing the format changes the string, which invalidates that one entry once — harmless, and worth knowing rather than rediscovering.

- [ ] **Promote the Content Security Policy from Report-Only to enforcing.** The policy, the report endpoint and its browser coverage have landed — see [Security](security.md#content-security-policy) and [D-260814c](decisions.md#d-260814c--ship-the-content-security-policy-report-only-and-accept-unsafe-inline). What remains is the judgement call the Report-Only phase exists to inform.
  - **Read the reports, not the console.** `/api/csp-report` logs one line per violation to the Vercel runtime logs, with extension noise already filtered. The console is specifically not the signal: a Maps `gen_204?csp_test=true` probe on `/travel` already fails as `ERR_BLOCKED_BY_CLIENT` for client-side blockers with no policy deployed at all, so a blocked probe cannot distinguish our header from the visitor's blocker. That single error is also the entire reason `/travel` scores **Best Practices 96**, and it must not later be misread as CSP fallout.
  - **The reports expire, so switch the emailing on before opening a window.** Vercel's runtime logs are a rolling buffer measured in hours to days, not the weeks this decision needs. Setting `CSP_VIOLATION_EMAILS=true` and redeploying makes them durable — see [Security](security.md#emailing-violations-temporary) — and switching it back off is part of closing the window, along with deleting `src/server/csp-mail/`.
  - **"Clean" has to mean covered, not just quiet.** Zero reports prove nothing if the path never ran. **Still unexercised: `/experience` with the YouTube embed actually playing.** `/travel` with Maps genuinely loading and `/contact` with a real submission were both covered by the 2026-08-15 window and came back with findings and silence respectively — BotID pulled no host the passive path had not already seen.
    - **Service-worker registration is no longer on that list.** `service-worker.spec.ts` now runs it under the deployed policy and produces no violation, so `worker-src 'self' blob:` has evidence behind it for the first time — see [D-260815a](decisions.md#d-260815a--give-the-service-worker-its-own-playwright-project-rather-than-unblocking-it-everywhere). Note the evidence is local and Chromium-only, so it does not discharge the cross-engine requirement below.
  - **The known allowlist gaps are closed, confirmed by a real observation window on 2026-08-15** — thirteen emailed reports over all five pages including a live contact submission, reducing to four distinct causes. `script-src` gained `'wasm-unsafe-eval'` and `connect-src` gained `https://mapsresources-pa.googleapis.com`, both exactly as predicted from the 2026-08-14 `next dev` run, so that run's evidence proved sound in production.
    - **The remaining two causes were not allowlist gaps at all**: nine of the thirteen reports came from inside the service worker, where `connect-src` governs fetches that `img-src` and `style-src` permit in a page. Fixed by confining the worker to same-origin caching rather than by widening the policy — [D-260815f](decisions.md#d-260815f--cache-only-same-origin-requests-so-the-service-worker-stops-rewriting-the-policy). **Expect these reports to keep arriving for a while**: clients hold the old worker until the new one activates, and under Report-Only that is log noise rather than breakage. Their disappearance is the confirmation that the fix reached real visitors.
    - **The Google Fonts entries are settled: both stay.** `style-src https://fonts.googleapis.com` and `font-src https://fonts.gstatic.com` outlived the vendoring because the Maps SDK requests three stylesheets of its own (Roboto/Google Sans, Google Sans Text, Material Symbols). The suspicion recorded here was correct, and it is now production-observed rather than assumed.
  - **Turbopack is not a violator, which removes one open question.** The concern that its HMR runtime would need `'unsafe-eval'` and flood development with noise was checked in the same run and is unfounded — it produced nothing.
  - **It must include Safari and Firefox — this is the one substantive thing still outstanding.** The 2026-08-15 window was single-engine, so it discharges nothing here. An allowlist tuned on Chrome-only reports is a known way to ship a policy that breaks elsewhere: the three engines name directives differently and Safari reports things Chrome does not.
  - **Promote the safe half now, rather than waiting on the allowlist.** `frame-ancestors`, `base-uri`, `form-action` and `object-src 'none'` do not depend on any allowlist being complete, and no report can change whether they are correct. Ship those as an enforcing `Content-Security-Policy` alongside the Report-Only header — both are valid together and browsers apply each independently — and keep only the resource directives under observation. **Deliberately deferred on 2026-08-15** to keep that change separate from the allowlist work; it remains the cheapest next step.
    - **Safari has already made the case for this half.** It logs _"The Content Security Policy directive 'frame-ancestors' is ignored when delivered in a report-only policy"_ on every page, following [CSP Level 2](https://www.w3.org/TR/CSP2/#directive-frame-ancestors) rather than Level 3 — so that directive currently neither blocks nor reports there, and no amount of further observation will change that. Promotion is the only thing that makes it live, and it also silences the message. Confirmed 2026-08-15 against the preview deployment; `X-Frame-Options: DENY` is what prevents framing meanwhile.
    - **Running both headers makes reports ambiguous**, because `src/server/csp/` records neither `disposition` nor which header fired. Carry that field through the parser, the log line and the email when the second header ships, or an enforced violation and an observed one will read identically.
  - **Promotion is a one-line change** — the header key in `next.config.js` — plus deleting the assertion in `security-headers.spec.ts` that the enforcing header is absent. Keep `report-uri` afterwards; an enforcing policy needs reports more than a Report-Only one does.
  - **Do not treat `'unsafe-inline'` as the thing to remove first.** It is permanent while BotID renders a nonce-less inline script and every page is statically prerendered ([D-260814c](decisions.md#d-260814c--ship-the-content-security-policy-report-only-and-accept-unsafe-inline)). Removing it is a separate, much larger question about whether these pages should render per request at all.
