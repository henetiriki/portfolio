  - **This migration was done twice.** The first pass shipped, then got reverted after review surfaced three real correctness gaps that a working build, a clean lint/type-check, and full visual QA had all missed — worth recording since none of them were hypothetical:
    1. **`postcss.config.cjs` silently dropped Next's own default PostCSS pipeline.** Next.js _completely disables_ its built-in Autoprefixer/flexbox-fixes/stage-3-feature-compilation the moment a project defines its own `postcss.config.cjs` — [documented behavior](https://nextjs.org/docs/pages/guides/post-css#customizing-plugins), not a bug, but easy to miss when the added config is scoped to "just what Mantine needs." The first-pass config had only `postcss-preset-mantine` + `postcss-simple-vars`, meaning the whole app would have shipped with **zero vendor prefixing** in production — invisible in Chromium-based tooling and in every check that was run, only surfacing on Safari/older browsers. Fixed by explicitly re-including Next's own default plugins (`postcss-flexbugs-fixes` + `postcss-preset-env`, copied verbatim from Next's default `postcss.config.json`) alongside Mantine's.
    2. **A hand-converted breakpoint used the wrong unit.** v6's `theme.fn.largerThan(1080)` (a non-token pixel breakpoint used in `portfolio.tsx`) converts _every_ breakpoint through `em()` at a 16px base — including raw numbers, not just named tokens (confirmed against Mantine's current `@mantine/emotion` compat-layer source, which reimplements this exact function to preserve v6 behavior). The first pass converted it to a literal `@media (min-width: 1080px)`; the correct conversion is `67.5em`. Identical at default browser zoom, which is exactly why it wasn't caught by visual QA — the difference only shows up when a user changes their browser's default font size, an accessibility setting `em`-based breakpoints track and `px`-based ones don't.

This is a legitimate pattern for genuinely dynamic values, but `variant` is a two-value enum known at build time — the idiomatic fix is a CSS modifier class (`.link.sm { ... }`), not a runtime-only custom property. The tell: a WebStorm "Cannot resolve custom property" inspection on the `var()` reads, which a `var(x, fallback)` doesn't satisfy (the fallback is a _runtime_ default, invisible to static analysis) but a modifier class sidesteps entirely, since every value then exists as ordinary CSS.

Full root-cause writeups live in [styling-theming.md](styling-theming.md#post-v7-visual-parity-fixes) (`global.css`'s four rules, plus component-level fixes); summary:
    - `WaveWrapper`'s hardcoded `h='10rem'` Box prop silently overrode the footer's top-wave `style={{ height: '5rem' }}` override, since v7's `getBoxStyle` always spreads style-props after the `style` object — the footer's top wave rendered 2x too tall.
    - Missing `img { vertical-align: middle }` (v6's normalize step had it, v7 has no equivalent) made the nav logo ~7.5px taller than it should be and visibly misaligned.
    - Missing `p.mantine-Text-root { margin: 1em 0 }` (v7's base stylesheet zeroes `<p>` margin unconditionally, v6 never overrode the browser default) removed paragraph spacing sitewide; restoring it globally then over-corrected two label-style `Text`s (`TimelineInstitution`, `TimelineLocation`) that explicitly wanted zero margin, fixed with `mt={0}` on each.
    - `color='shamrock'` (no shade) on outline-variant buttons resolved to shade `0` in dark mode via Mantine's `primaryShade`-derived outline-color formula (`primaryShade: 4` → shade `4-4=0`) — the "Send"/"Let's chat"/`ErrorContent` buttons rendered nearly invisible instead of green. Fixed with explicit `color='shamrock.4'`.
    - One `Anchor` was left on `color='shamrock'` (Button-variant-only prop) instead of `c='shamrock'` (the actual text-color prop) after the mechanical `sx`→prop conversion, rendering with no color at all.
    - `Anchor`/`Text` no longer set their own `font-size`/`font-weight`/`font-family` in v7 (relies on inheritance). Two places initially patched only the font-size symptom with a hand-written `font-size: inherit` CSS rule, leaving `font-weight` still wrong; replaced with Mantine's own `inherit` prop (v7's renamed equivalent of v6's `Text inherit`), which fixes size/weight/line-height together.
    - A `<Text>` (no `inherit`, no `span`) wrapping a card title inside a `<Title>` rendered at Mantine's default 14px/400 instead of inheriting the heading's 24px/700 — simplified by dropping the redundant wrapper entirely.
    - `FooterContainer`'s `ff={theme.headings.fontFamily}` prop was a dead v6 no-op (`Text`/`Anchor` always won with their own explicit `font-family` back then) that became live and harmful in v7, rendering the entire footer in the heading font instead of body text.
    - `--mantine-color-error`'s v7 dark-scheme default (`red-8`) didn't match this app's desired lighter `red-4` for validation errors/required asterisks. The first override attempt (`html[data-mantine-color-scheme='dark']`) silently lost to Mantine's own `:root[data-mantine-color-scheme="dark"]` rule — `:root` is a pseudo-class, so it out-specifies a plain element selector; fixed by matching that specificity (`html:root[...]`).
    - `ContactForm`'s message `Textarea` had `minRows={4}` but not `autosize` — Mantine only honors `minRows`/`maxRows` when `autosize` is also set, so the field silently used its ~2-row CSS `min-height` instead.

- [ ] **Migrate off deprecated `google.maps.Marker`.** Every marker on `/travel` logs `As of February 21st, 2024, google.maps.Marker is deprecated... use google.maps.marker.AdvancedMarkerElement instead` — not yet discontinued (12 months notice required before that happens), but bug fixes have stopped. **A previous attempt at this migration was made and not completed** — worth understanding why before retrying, since it's a genuinely bigger lift than the warning suggests, not a drop-in rename:
  - `Marker.tsx` is built entirely on the classic imperative `Marker` API — `new google.maps.Marker()`, `.setOptions()`, `.setIcon()`/`.getIcon()` (for the zoom-based icon rescaling), `.setAnimation(google.maps.Animation.DROP | .BOUNCE)` (both the staggered drop-in and the click-to-bounce interaction), `.setMap(null)` for cleanup.
  - `AdvancedMarkerElement` supports **none of these** the same way: no `Animation` enum at all (drop/bounce would need to be reimplemented as custom CSS/Web Animations API), icon rendering is a `content` DOM node instead of an `icon: google.maps.Symbol`, `.setMap()` is replaced by a `map` property, and it requires the parent `Map` to be constructed with a `mapId` (this app's `Map.tsx` doesn't currently set one). This touches most of `Marker.tsx`'s logic (`clickEventListener`, `zoomEventListener`, the drop-in `cancelableDelay` staggering, the `markerScale`/`getZoomMarkerWeightExponent` icon-scaling-on-zoom feature), not just the constructor call.
  - `MarkerLegend.tsx` likely also needs attention if it renders anything icon-shaped using the same `google.maps.Symbol` assumptions — not yet audited.

## Bug fixes

- [x] **Audit & fix the Google Maps layer regressions.** Done 2026-08-06. Code-reading audit (comparing `Marker`'s and `Polyline`'s call sites in `MapWrapper.tsx`) turned up two confirmed regressions from the vanilla-JS→React port:
  - **Marker drop-in staggering was broken.** `Marker`/`Polyline` both stagger their drop-in animation via `cancelableDelay(idx * order * 100, ...)` — a multiplication, so `idx === 0` always produces a `0` delay regardless of `order`. `Polyline`'s call sites already dodged this (`idx + 1`); `Marker`'s didn't, so the first airport/station/port marker in each group dropped simultaneously instead of staggering. Fixed in `MapWrapper.tsx` by passing `idx + 1` to `Marker`, matching `Polyline`'s existing pattern.
  - **Zoom reset on resize.** `Map.tsx`'s viewport-size effect forced `zoom` back to the breakpoint default on every `width` change, not just initial mount — so resizing the window after the map loaded would silently discard the user's manual zoom. Fixed by tracking initial setup with a ref (`initialZoomSetRef`) so only `minZoom` stays reactive to viewport width after the first render; `zoom` is set once.
  - Both fixes are covered by regression tests in `components/travel/__tests__/` (`Map.test.tsx`'s "does not force zoom again on a later resize", `MapWrapper.test.tsx`'s "never passes idx=0 to a marker").
- [x] **Fix `useDeepCompareEffectForMaps`'s dead custom-equality comparator.** Done 2026-08-07, found while pushing coverage on this hook — line-by-line coverage staying at 0% for the comparator body despite passing tests was the tell. `createCustomEqual` was called with a factory function (`deepEqual => (a, b) => {...}`), which was the correct API for an old `fast-equals` major version but not the installed `fast-equals@5.4.1`, whose `createCustomEqual` takes an **options object** instead. Since a function is also an object, the mismatched call didn't throw — it silently destructured to all-`undefined` options, making the hook fall back to plain structural deep-equal with zero LatLng-awareness. Existing tests didn't catch it because they only compared plain `{lat,lng}` literals, where structural equality coincidentally agrees with the intended `.equals()`-based comparison; the bug only bites real `google.maps.LatLng` **instances**, which expose coordinates via `.lat()`/`.lng()` methods rather than plain properties. Fixed by correctly using `createInternalComparator` (which only intercepts _nested_ property comparisons) plus a wrapper for the top-level entry point (which fast-equals calls directly, bypassing `createInternalComparator` entirely) — both needed, confirmed via `node_modules/fast-equals`'s own source. New tests cover a LatLng-shaped field nested inside a compared dependency object, which the old (broken) implementation would have gotten wrong.
- [x] **Fix a live-`Set` mutation bug in the Google Maps test mock causing a heap OOM.** Done 2026-08-07, found while writing a test for `Map.tsx`'s recursive `zoomMap` animation — the same test area a prior session had abandoned after an OOM crash (previously misattributed to `jest.useFakeTimers()` + `advanceTimersByTimeAsync`). Root cause was actually in `src/utils/test/googleMapsMock.ts`'s `triggerMapsEvent`: it iterated the **live** `Set` of registered listeners via `.forEach()`. `zoomMap`'s recursive `zoom_changed` handler synchronously registers a new listener on that same event as part of running — and `Set.forEach` visits elements added mid-iteration per spec — so the new listener fired immediately in the same synchronous pass, which registered another, which also fired immediately, unboundedly. Real event systems (DOM, Node's `EventEmitter`) snapshot listeners at dispatch time specifically to avoid this; the mock didn't. Fixed with a one-line snapshot (`[...handlers].forEach(...)`) — confirmed safe via a capped-heap (`--max-old-space-size`) reproduction before and after, and a full suite run afterward. This unblocked testing `Map.tsx`'s zoom-stepping animation directly (previously untested, now 100% covered) and was a test-infrastructure bug, not a production one.
