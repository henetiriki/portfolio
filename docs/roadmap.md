# Roadmap

Open work only. Completed milestones are recorded in [Project History](project-history.md), durable rationale in [Engineering Decisions](decisions.md), and current behaviour in the topical documentation. Items are grouped by area rather than strict priority; each should normally be delivered as its own scoped change unless a dependency is called out explicitly.

Last reviewed: 2026-08-14.

## Testing & automation

- [ ] **Enforce required checks on `main` — waiting on repository visibility, not on configuration.** CI uploads Jest's explicit LCOV report to Codecov through short-lived GitHub OIDC authentication, with a strict 100% patch target and source-line annotations. Reporting works; blocking does not, and cannot yet.
  - **This is not a settings toggle.** Verified 2026-08-11: both the classic branch-protection API and the newer rulesets API return `403 Upgrade to GitHub Pro or make this repository public to enable this feature`. Required status checks are unavailable for a private repository on a free personal plan, so no amount of repository configuration will enable them.
  - **Decision: make the repository public once the remaining actionable roadmap items are done**, then require both `CI / Validate & build` and `codecov/patch` on `main`. Publishing is preferred over a paid plan for a personal portfolio site whose source is not sensitive.
  - **Before publishing**, enable Cloudinary's **strict transformations** and restrict `fetch` delivery. The cloud name is unavoidably public — it appears in every delivery URL and is already inlined in the shipped client bundle — so anyone can request arbitrary on-the-fly transformations and burn transformation credits. That exposure exists today; publishing simply makes the account easier to notice. This is a billing-abuse control, not a data-exposure one.
  - **Also before publishing**, confirm the repository history carries no secrets. `.env` and `.env.test` are tracked but hold only non-secret or dummy values; real credentials live in `.env*.local`, which is gitignored. That is the current state — history should still be checked rather than assumed, because publishing exposes every past commit, not just the tip.

- [ ] **Extend the browser regression suite.** The harness and its first specs have landed — see [Development Workflow](development.md#browser-regression-suite). Remaining candidates, still deliberately narrow:
  - Consider a reduced-motion pass (`prefers-reduced-motion`), since the map reveal, marker drop and smooth scrolling all branch on it. Playwright can set it per project via `use.reducedMotion`, so this is a project variant rather than new specs.
  - Consider covering the footer's own scroll-to-top control, which shares `pageTopRef` with the header's but has a separate call site.

- [ ] **Cover PWA installability in the browser suite.** Nothing currently asserts that the app is installable. The service worker is guaranteed to be _generated_ — CI asserts `public/sw.js` is non-empty after every production build ([D004](decisions.md#d004--generate-the-service-worker-in-every-production-build-never-in-development)) — but generation is not installability, and the browser suite deliberately sets `serviceWorkers: 'block'` so it exercises none of it. Beyond that, this is manual QA only. Split it, because the two halves have very different costs:
  - **The manifest half is testable today**, with no service worker involved, so it sits happily inside the existing projects. Assert that `<link rel="manifest">` is present, that the manifest fetches and parses, that `display` is `standalone`, and that `name`, `short_name`, `start_url`, `theme_color` and `background_color` are all set.
  - **The highest-value assertion is that every referenced asset returns `200`** — the manifest's icons and shortcut URLs, and the 35 icon and splash-screen `<link>` tags in `_document.tsx`. A renamed or moved file breaks installability (or the splash screen) silently: the build still succeeds, no test fails, and the first sign is an install prompt that never appears. Nothing today would notice.
  - **Worth knowing before touching the icons:** `public/manifest.json` declares four icon entries but only two files exist — `manifest-icon-192.maskable.png` and `manifest-icon-512.maskable.png`, each listed twice, once as `purpose: any` and once as `maskable`. That satisfies Chrome's requirement (≥192 and ≥512 in `any`), so installability is fine, but a maskable image used as `any` carries its own safe-zone padding and therefore renders inset wherever the platform expects full-bleed. Fixing that is a separate cosmetic call; the point here is that it is deliberate-looking duplication a tidy-up could easily break.
  - **The service-worker half needs its own Playwright project** with `serviceWorkers` left at its default, isolated from the others so its cache cannot pollute them. One spec: registration succeeds and a fetch handler is active. This is the more expensive half and the less urgent one, since the CI build assertion already catches the failure mode where no service worker is produced at all.
  - **Do not chase offline coverage here.** The goal is installability, not the offline experience; `/_offline` remains a manual check on the [release checklist](release-checklist.md#after-deploy).

- [ ] **Pin the Yarn CLI by integrity hash so Corepack stops fetching it unverified.** `packageManager: "yarn@4.18.0"` in `package.json` carries no hash, so every run prints `! Corepack is about to download https://repo.yarnpkg.com/4.18.0/packages/yarnpkg-cli/bin/yarn.js` and then executes what comes back with nothing to check it against. `corepack use yarn@4.18.0` rewrites the field with an integrity hash appended (`yarn@4.18.0+<algorithm>.<hash>`), after which Corepack verifies every later download against it.
  - **The fetch is redundant as well as unverified**, which is what makes this both cheap to fix and easy to overlook. The identical release is already vendored at `.yarn/releases/yarn-4.18.0.cjs` and `.yarnrc.yml` points `yarnPath` at it, so the downloaded CLI's only remaining job is to hand off to a binary the repository already contains. `actions/setup-node` had likewise already resolved `yarn: 4.18.0` on `PATH` before the `corepack enable` step ran.
  - **This is the missing half of [D008](decisions.md#d008--keep-the-package-managers-supply-chain-defaults).** That decision deliberately keeps Yarn's install-time protections on — the `1d` minimal age gate, the empty git-repository allowlist, disabled install scripts. Those govern what Yarn is allowed to install; nothing currently governs how Yarn itself arrives.
  - **Keep `corepack enable`.** Removing the step would contradict `README.md` and [Development Workflow](development.md), which both document Corepack as the supported path. Adding the hash closes the gap without changing how anyone works, locally or in CI.

- [ ] **Tidy the Playwright browser cache step, whose comment no longer describes what it does.** Three small things in one step of `.github/workflows/ci.yml`, all verified against the 2026-08-14 run. None is a defect; all three mislead the next reader.
  - **The stated cache key is not the real one.** The comment says the browser is cached "on the Playwright version" and "changes only when the package does", but the key is `hashFiles('yarn.lock')`, so any dependency change anywhere in the lockfile discards it and forces a fresh download. Either narrow the key to the resolved Playwright version, which is what the comment promises, or correct the wording to match the lockfile-wide key.
  - **The stated size is wrong.** The comment says the download is "~100 MB"; the run restored 269 MB. Worth correcting whichever way the key question lands — it is the same drift the [documentation sweep](release-checklist.md#documentation-sweep) already guards against in prose.
  - **`id: playwright-cache` is declared and never read.** Nothing consumes `steps.playwright-cache.outputs.cache-hit`, which normally means a conditional skip was intended and never wired up. Skipping the whole step on a hit would be wrong, though: `playwright install --with-deps chromium` also installs system dependencies, and on the 2026-08-14 cache hit it still ran `apt-get update` and pulled nine font packages (21 MB, ~13s). Unconditional `--with-deps` is the safe default, so either gate only the browser download on that `id` or drop the `id`.

## Framework & dependency upgrades

- [ ] **Self-host the web fonts with `next/font/local` to make builds hermetic.** `next/font/google` downloads the font files from `fonts.gstatic.com` at build time, so every build depends on that host being reachable. On 2026-08-13 a CI build failed on exactly this (`Failed to fetch font file from https://fonts.gstatic.com/...montserrat...woff2`, retried and failed) while the Vercel build of the same commit succeeded — a runner-network problem, not a code one. It was the first such failure in the previous twelve runs, so it is transient rather than systemic, but the dependency is real and avoidable.
  - **Smaller than it looks: two files, ~72KB.** The build emits 14 `woff2` files totalling 368KB, but only two are ever fetched — the preloaded latin subsets (Montserrat 37KB, Roboto 35KB). The other twelve are unicode-range subsets a browser pulls only if a glyph demands one.
  - **Two files are provably enough for this content.** The whole of `src/` contains 13 non-ASCII characters (`ã æ é í ô ö ø ü – — ' " "`). Every one falls inside Google's `latin` unicode-range: the accented characters are all ≤ U+00FF, and the typographic dashes and quotes sit in U+2000–206F, which that range covers. The site's text is static fixtures, so there is no user-generated content that could later need a subset that was not shipped.
  - **Ship the licences with the files.** Montserrat is OFL 1.1 and Roboto is likewise openly licensed; both permit bundling _provided the licence text travels with the font_. This matters more once the repository is public — see the visibility item above.
  - **Verify rather than assume one thing:** Next currently generates size-adjusted fallbacks (`Montserrat Fallback`, `Roboto Fallback`) to limit layout shift. `next/font/local` supports this, but confirm those `@font-face` rules still appear in the built CSS rather than trusting that they carry over.
  - **Exposure is already halved.** CI used to build twice and so fetched the fonts twice per run; removing the `WITH_PWA` flag on 2026-08-14 cut it to one build. Only self-hosting removes the dependency entirely.

- [ ] **Adopt the native TypeScript 7 toolchain when ecosystem support is ready — blocked.** The project now uses TypeScript 6, the supported JavaScript-based bridge release, with its configuration deprecations already removed. The 2026-08-09 TypeScript `7.0.2` trial still failed before compilation because Yarn's built-in compatibility patch expected `lib/_tsc.js`, which the native Go distribution does not ship; `typescript-eslint@8.66` also requires TypeScript `<6.1.0`. Recheck only when Yarn supports the native distribution and TypeScript-ESLint supports its compiler API strategy; both conditions are required.

- [ ] **Upgrade Babel 7 to 8 when Jest supports it — blocked.** The app compiles with SWC and has no Babel configuration; Babel is a direct development dependency solely for Jest. `jest-config`, `@jest/transform` and `jest-snapshot` still depend on Babel 7, so follow Jest's support rather than forcing an app-irrelevant major ahead of its consumer.

- [ ] **Upgrade Node.js 24 to 26 on or after 2026-10-28.** The project follows Active LTS releases, and Node 26 does not reach that status until then. Confirm Vercel support first, then update `engines.node`, `.nvmrc` and `@types/node` together and validate installation, native dependencies, the full suite and both build modes on the new runtime. See [D002](decisions.md#d002--track-active-lts-nodejs-releases).

## Performance, SEO & platform polish

- [ ] **Close the remaining accessibility gap on `/experience`.** After the YouTube embed was deferred, mobile PageSpeed returned Performance 93, Best Practices 100, SEO 100 — but **Accessibility 98**. The project's own axe pass is clean across `wcag2a`/`wcag2aa`/`wcag21a`/`wcag21aa` with third-party frames excluded, so whatever Lighthouse is reporting is either outside those tags or something axe does not cover. Read the report's accessibility section before changing anything rather than guessing at it. If it turns out to be a real gap in our own markup, it is also a candidate for the browser suite, since that suite already runs an axe pass per page template and would be the natural place to stop it recurring.

- [ ] **Introduce a Content Security Policy.** Ship it in Report-Only first and promote it only once the reports are clean, because Maps, BotID, Vercel telemetry and remote images all need an allowlist. The deprecated `X-XSS-Protection` header has already been removed, so this is the remaining half of the security-header work.
