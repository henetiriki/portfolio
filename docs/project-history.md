## 2026-08-22 — Retire release tags and application-version bumps

- **The release-tag roadmap item is closed without adding tags, GitHub Releases or application-version bumps.** A squash merge is already the repository's immutable change identifier, carrying its pull request number; the commit's Vercel status links a completed production deployment to the exact build. The most recent completed deployment, rather than `main`'s tip, answers what is live when a documentation-only merge is ignored.
- **Tags did not add the capability the item sought.** They would alias a commit without recording whether Vercel built or promoted it. Automating them correctly would require deployment-completion state, credentials and gating for failures and ignored builds — overhead for a site with no release artifact or compatibility contract. See [D-260822b](decisions.md#d-260822b--use-merged-commits-and-vercel-deployments-as-the-release-record-rather-than-tags).
- **A pull request number is the precise history citation when one is needed**, retaining the review and CI context a generated version would discard. Vercel's deployment history remains the runtime and rollback record.

## 2026-08-21 — Exclude the Apple splash images from the precache manifest

- **The 42 splash images no longer ship in the service worker's precache manifest** — [D-260821h](decisions.md#d-260821h--reproduce-the-public-directory-precache-scan-to-exclude-the-apple-splash-images), closing the second follow-up on the splash-matrix roadmap item now that the generator is committed. They cost roughly 1.6 MB into every installed app to serve at most one file, fetched directly by iOS rather than through anything the worker's `runtimeCaching` list could intercept.
- **`@serwist/next` turned out to expose no way to exclude specific files from `public/`.** Its `globPublicPatterns` option takes only positive include patterns, and the `glob` package it's built on dropped `!`-prefixed pattern negation in v6 — confirmed by reading both packages' source rather than assumed from the README, which documents neither option in enough depth to answer the question either way. `manifestTransforms` looked like the fix at first and isn't: it only ever sees webpack's own compiled JS/CSS assets, because `public/`'s scanned files are appended to the manifest through a separate, later step (`additionalPrecacheEntries`) that transforms never run against — traced through `@serwist/build`'s `transformManifest` to be sure rather than inferred from behaviour.
- **The fix is `next.config.js` supplying `additionalPrecacheEntries` itself**, reproducing @serwist/next's own public-directory scan (recursive walk, MD5 `revision` per file) minus anything matching `apple-splash-\d+-\d+\.png`. Providing that option at all skips the library's own scan entirely, which is what makes reproducing it necessary rather than optional — there was no smaller change available.
- **The first version precached a stray `.DS_Store`.** `glob` ignores dotfiles by default; `fs.readdirSync` does not, and this repository's own `public/.DS_Store` (Finder-browsed on this machine, gitignored, never committed) proved it by showing up in the generated manifest. Would not have reproduced on a clean CI checkout, but the reimplementation was wrong regardless of whether this instance of it was ever observable in production — fixed by excluding dotfile names to match `glob`'s actual default.
- **Verified against the live registered worker, not just the built file.** `service-worker.spec.ts` opens the real `caches` API after registration and asserts a known icon stayed precached while no splash image got in; confirmed to fail (splash image present) with the exclusion reverted and pass with it restored.
- **Whether the iOS home-screen splash still renders offline was explicitly not verified by the change itself.** `apple-touch-startup-image` is WebKit-only and Chromium-based Playwright cannot observe it; research into whether it shares iOS's service worker cache at all turned up thin, inconsistent public documentation rather than a clear answer. Left as an open item with a manual check named rather than assumed safe, since no physical iOS device was available to test on directly.
- **Verified the same day anyway, on an iOS Simulator.** The preview deployment was added to an iPhone 17 Pro simulator's (iOS 26.5) home screen, confirmed to show the splash online, then force-quit and relaunched with the host Mac's own Wi-Fi switched off — the Simulator exposes no independent network toggle in iOS 26's Settings. The splash still rendered. Recorded in [D-260821h](decisions.md#d-260821h--reproduce-the-public-directory-precache-scan-to-exclude-the-apple-splash-images) with the caveat a Simulator carries relative to physical hardware.
- **The staleness-detection follow-up remains open on its own**, deliberately not folded in here.

## 2026-08-21 — Assert icon contrast directly, scoped to what axe cannot see

Confirmed live in a browser before being trusted, then reproduced as a failing test, then fixed by giving the icon `black-russian.4` on hover — the same pairing D-260821a already established for `shamrock.4` (11.39:1) rather than a new one.

## 2026-08-21 — Commit the PWA icon and splash generator, since it had never been

- **`scripts/generate-pwa-icons.mjs` recreates the whole matrix `git rm`d nothing could reproduce.** [D-260815e](decisions.md#d-260815e--generate-the-pwa-icon-and-splash-set-from-one-vector-master) generated 49 files from `ouwl.svg` and never committed the script that did it, leaving the assets themselves as the only record — regenerating meant rewriting it from scratch, exactly the trap the roadmap item flagged.
- **The device table is read out of `AppleSplashLinks.tsx`, not duplicated.** The script parses `SPLASH_DEVICES` with the TypeScript compiler API, the same technique `generate-mantine-css-variables.mjs` already uses for `colors.ts`. A second, hand-copied device list would have reintroduced the exact drift risk this work exists to close.
- **The original scale constants were gone, so they were measured back out of the committed PNGs rather than guessed.** Comparing each icon type's rendered owl size against its canvas gave `any`/`apple-icon` ≈ 62%, `maskable` and `monochrome` ≈ 55%, and splash exactly the documented 35% of the short edge — monochrome then rendered byte-for-byte identical to the previously committed file, which is the strongest evidence available that the recovered constants, not just the visual result, match what actually produced the current set.
- **Monochrome needed no alpha-channel surgery**, despite looking at first like it would: recolouring the SVG's eye fill to match the owl outline before rasterising collapses the two-colour mark into a flat silhouette on its own, since the shape's antialiased edges already carry the right alpha. No `extractChannel`/`joinChannel` composition was needed.
- **Regenerating produced smaller files than the set it replaced**, not just reproducible ones: bumping `compressionLevel` to 9 (sharp's default is 6) took the directory from the roughly 2 MB the roadmap cited to 1.6 MB, splash images included, which is a straightforward corollary of committing the generator rather than a goal pursued on its own.
- **The three `favicon-*.png` files are explicitly untouched.** They predate this script by four years and were never part of what [D-260815e](decisions.md#d-260815e--generate-the-pwa-icon-and-splash-set-from-one-vector-master) regenerated; the boundary is recorded in [PWA & SEO](pwa-seo.md#progressive-web-app) so it doesn't read as an oversight later.
- **Precache exclusion and a staleness check remain open** — see [Roadmap](roadmap.md#performance-seo--platform-polish) — deliberately left for their own changes rather than folded in here.

## 2026-08-21 — Extend the browser suite with reduced motion and the footer's own scroll-to-top

- **Two roadmap candidates landed in one pass**: a `reducedMotion: 'reduce'` project variant, and coverage for the footer's own `scrollToTop` call site, which shares `pageTopRef` with the header button's but fires from a nav link's `onClick` rather than a dedicated control.
- **Reduced-motion coverage has to observe the call itself, because the destination is identical either way** — `scrollY` ends at 0 whether `scrollIntoView` ran with `'auto'` or `'smooth'`. `captureScrollIntoView` (`e2e/support/helpers.ts`) patches `Element.prototype.scrollIntoView` to record the `behavior` a real navigation receives; `reduced-motion.spec.ts` runs in its own filename-routed project, `reduced-motion-chromium`, and asserts `'auto'`.
- **The first version of the footer test was vacuous, and only deliberately breaking the code caught it.** Clicking a footer nav link back to the current route resets `scrollY` to 0 on its own, through Next's router — a `scrollY`-based assertion kept passing with `onClick={scrollToTop}` deleted from `Footer` entirely. Replaced with the same `captureScrollIntoView` capture, asserting the call happened rather than its side effect; confirmed to fail without the prop and pass with it restored, the same way the reduced-motion assertion was confirmed to fail without `reducedMotion: 'reduce'` set.
- Both additions keep the suite at zero skips: `reduced-motion.spec.ts` is routed to its project by filename, the same convention the mobile/desktop/service-worker specs already use.

## 2026-08-16 — Reclaim the left gutter on the experience timeline

- **Body copy on `/experience` went from half the screen to two thirds of it** at mobile widths — [D-260816k](decisions.md#d-260816k--reclaim-the-timelines-gutter-from-the-container-not-from-the-rail). Three of the five stacked layers now respond to the viewport; the rail's own offset and the heading icon are untouched.
- **The roadmap's figure understated it.** The item recorded the column as 211px at 375px, which is the distance from the text to the card's right _edge_ — it does not subtract the card's own right padding. Measured, the readable column was 186px, and half the screen was gutter rather than 44% of it.
- **The container turned out to be both the biggest win and the safe one, which inverted the expected order of work.** The item flagged `TimelineBox`'s padding as the safe change and the rail as the dangerous one, correctly. What it did not say is that the icon and the rail are both measured from the container's content edge, so moving that edge moves them together — the un-centring trap applies to changing the rail's margin, not to changing the box the margin is measured from.
- **The arithmetic-led value was wrong, and only the screen showed it.** Taking `TimelineBox`'s padding to 24px cleared the rail by 5px and read as a clean result; the card's arrow is drawn 20px _outside_ the card, into the gap the dot occupies, so the tip went through the dot. The padding stops at 32px with the arrow narrowed below `xs`. That floor is recorded nowhere in the markup and was absent from the roadmap item's list of constraints.
- **Measurement was nearly taken from the wrong tree twice.** The agent preview server serves the repository's launch directory, not the worktree, so the first round of "verification" measured `main`. A backgrounded browser tab also returns zeroed rects, which reads as a broken selector rather than a stale viewport.
- **The rail moved after all, 12px, on review.** The first version left it alone as too dangerous. Asked whether the icons could break the grid so the rail sat as far from the left as the card sits from the right, four variants were rendered and measured rather than argued: full symmetry buys 20px and puts the icons 4px from the screen edge, the halfway position buys 12px at a 12px overhang. The halfway one shipped. Recorded because the rejected variant is the one that sounds obviously right — see [D-260816k](decisions.md#d-260816k--reclaim-the-timelines-gutter-from-the-container-not-from-the-rail).
- **Mantine emits a responsive style prop as a `<style>` element immediately before the element carrying it**, which broke the new spec's DOM traversal twice — once on `firstElementChild`, then again on `nextElementSibling` when the rail's own margin became responsive. Both times it read as a wrong selector rather than an extra node. The traversal now looks for a `div` at every step instead of assuming which one is affected.
- **The new spec was confirmed to fail on the old layout before it was believed.** Both column assertions fail there and the four alignment assertions pass, which is the intended split: the first pair guards the fix, the second guards against a future fix that reclaims width by breaking the rail-to-icon or arrow-to-dot relationship.

## 2026-08-16 — Watch project coverage, and retire two roadmap items that held no work

- **Codecov's whole-project status is on, as `informational: true`, and Jest's global floor moves 80% → 95%** — [D-260816i](decisions.md#d-260816i--watch-project-coverage-without-blocking-on-it). The gap being closed is that `codecov/patch` only judges changed coverable lines, so a change deleting a test file passes trivially while project coverage falls, and an 80% floor sat too far below the truth to notice.
- **The first proposal was to skip the status entirely and only raise the Jest floor; review redirected it.** The argument for skipping was that a status which never blocks earns nothing an in-repo floor does not — and it is wrong in one specific way that made it worth keeping: a fixed floor cannot ratchet. It tolerates the same 5-point drop forever, whereas `target: auto` re-baselines every merge. The informational form takes the ratchet and declines the merge gate, which is the combination neither original option offered.
- **Requiring the project status stays rejected**, because it is a comparison where `codecov/patch` is not, and the dropped-upload failure this repository has actually seen would land on it alone.
- **`hide_project_coverage` flips to `false` alongside it**, since it was `true` for a reason that expired with `project: off`. Left set, the new delta would have lived only in a status description behind an expand — a ratchet with its report suppressed.
- **Codecov has nothing graphical at pull-request scale**, established while asking whether it should. The sunburst is whole-repository, the comment and statuses are text, and the one visual aid is the GitHub Checks annotation — which **Codecov is deprecating**, because GitHub's API cannot clear an annotation once sent, so one from an earlier push outlives the commit that covered the line. Annotations are also silently disabled by configuring Flags or Components. Jest's `lcov-report` HTML is richer but local, and hosting it would duplicate the annotations for more machinery.
- **The fork item was deleted rather than actioned, and it was wrong.** It said a fork pull request could not merge "without using the ruleset's bypass" — the ruleset has no bypass actors and reports `current_user_can_bypass: never`, by [D-260816c](decisions.md#d-260816c--keep-the-ruleset-free-of-bypass-actors-and-accept-the-wedge-risk). The only route is editing the ruleset. The corrected consequence moved to [Testing](development.md#testing), where the fork upload skip it follows from was already documented; the [Roadmap](roadmap.md) holds open work, and this was a fact.
- **Both items' live state was verified before either was touched**, which is how the bypass error surfaced: `gh api repos/henetiriki/portfolio/rulesets/<id>` for the check set, and Codecov's API for activation.
- **Jest and Codecov disagree on statement coverage, and neither is wrong.** Jest reports 99.93% statements against 100% branches, functions and lines; Codecov reports 100%. LCOV records lines, branches and functions but has no statement counter at all, so Codecov never sees the metric that differs. Worth knowing before the discrepancy is chased as a dropped upload.

## 2026-08-16 — Put the type scale back on Mantine's defaults

- **Body copy is 16px.** Every `fontSizes` token sat one step below Mantine's own since the v7 migration, and `Text` defaults to `md`, so every paragraph on the site rendered at 14px beneath headings on a conventional scale — [D-260816f](decisions.md#d-260816f--put-the-type-scale-back-on-mantines-defaults-and-make-leading-a-ratio). Two files changed.
- **The leading mattered more than the sizes.** `body` carried an absolute `line-height: 1.5rem`, so larger text got proportionally tighter: 1.71 at 14px, 1.33 at 18px. A unitless `1.5` tracks whatever size it lands on, and without it the sizes alone would have made the largest text worse.
- **Dropping the contact form's `size='lg'` would have shipped an iOS zoom defect.** The plan treated it as a workaround made redundant by a larger `md`; measuring showed `Input` defaults to `sm`, not `md`, so removing the prop rendered the fields at 14px and shrank the control from 50px to 36px. It sets a deliberate control height rather than compensating for anything, and it stays.
- **A Mantine control's box does not scale with the token.** `--input-height` and `--button-height` are per-size constants; only the `-fz` variables read the theme. The form's text grew inside boxes that did not.
- **Verified by measurement across all five routes rather than by eye**, since the browser pane was hidden for much of it and layout read zero. Computed font sizes and Mantine's own CSS variables resolve regardless, which is what the checks used.
- **Confirmed on an iOS simulator afterwards**, which is what the zoom claim actually needed: focusing the 18px name field on an iPhone 17 Pro left the layout scale unchanged, Safari only scrolling the field above the keyboard.
- **About half the site's text never read the scale** and is untouched — header navigation, page sub-headings, timeline entries, map markers, portfolio cards. Reviewing those is now [open work](roadmap.md), agreed rather than assumed: the visible before/after was checked against expectations, and two items on the "unchanged" list had in fact moved — the home page's `ex-flight attendant` line (14px → 16px) and the footer's navigation links (16px → 18px), both `Text` defaults rather than hardcoded.

## 2026-08-16 — Give the browser suite its own port, and every branch a prefix

- **The browser suite serves on 3001, and 3000 is now reserved for `next dev`.** Both an agent and a human wanted 3000 at once — one to run `yarn test:e2e`, the other to watch changes land — and `reuseExistingServer` outside CI meant Playwright attached to whatever it found rather than starting the server it meant to test. [D-260816g](decisions.md#d-260816g--serve-the-browser-suite-on-3001-and-leave-3000-to-next-dev).
- **The pin to 3000 had been stated as non-negotiable in four places, and was already obsolete.** The reason given — the Maps key being origin-restricted — is true of the key and irrelevant to the suite, because `blockGoogleMaps` aborts every `googleapis.com` request in every spec, including the one asserting the travel page's error state, which depends on that abort. The restriction still governs manual QA under `yarn dev`, which is what 3000 is now kept for.

## 2026-08-15 — Harden the shell-hygiene controls for Auto mode

- Adopting Auto mode changed what the permission allowlist is worth, so `.claude/settings.json` was revisited: the hook pattern is now `&&|;|[|][|]`, `Bash(git stash *)` is gone from the allow list, and [D-260814b](decisions.md#d-260814b--enforce-shell-hygiene-with-a-hook-rather-than-a-convention) records which of its two original justifications survived. [`AGENTS.md`](../AGENTS.md) carries the widened rule.
- **`||` was blocked because the trigger for blocking it had quietly stopped firing.** The original carve-out said to widen the pattern if `||` ever appeared in practice — but the observer was the permission prompt, and Auto mode does not prompt for allowlisted commands. `||` launders exactly as `&&` does: it matches `Bash(git add *)` in `git add . || <anything>`, and slips past a soft-deny rule that anchors at the start of the command.
- **A character class rather than escaped pipes**, so no backslashes have to survive both the JSON and the jq layer.
- **`git stash` was allowlisted despite `AGENTS.md` forbidding it.** Survivable while a prompt still sat in front of most commands; under Auto mode it is an unreviewed grant for the one operation most likely to lose a concurrent session's work, since the stash stack is shared across worktrees.
- **Hook changes take effect immediately, unlike permission rules.** Verified in the session that made this one — the edited hook refused the very next command carrying `||`, and then refused the commit describing it. `AGENTS.md`'s warning that `.claude/` changes wait for a session restart holds for permission rules only.

## 2026-08-14 — Stop `git -C` from defeating the permission allowlist

- [`AGENTS.md`](../AGENTS.md) gains a shell-hygiene rule against passing `-C <path>` to `git`, and `.claude/settings.json` gains the bare no-argument forms of the four read-only check scripts plus `git check-ignore` and the browser `find` tool.
- **Found from the symptom, not from a review.** Git commands started prompting for approval again, and the allowlist looked untouched because it was — the commands had changed shape. `Bash(git add *)` matches by prefix and never sees `git -C /path/to/repo add`, and the harness's own auto-allow for read-only git reads the token after `git`, finding `-C` rather than `status`. Ten `git -C … status` calls, seven `log`, seven `grep` and five `commit` in one session all fell through to a prompt.
- **The habit came from avoiding `cd`.** The rule that the working directory persists between calls is what makes `-C` pointless, so reaching for it to honour that rule inverts it. Both defeat the allowlist for the same reason chaining does: matching runs against the whole command string.
- **Widening the rules was rejected as the fix.** `Bash(git -C * )` would allowlist `push --force` and `reset --hard` along with everything else, and per-subcommand `-C` variants would double the list to accommodate a habit with no reason to exist.
- **The four check scripts were listed only as `yarn X *`.** That form matches by prefix and needs the trailing space, so a bare invocation may not match — and bare is how they are run: `prettier:check` 11 times, `type-check` 7, `eslint:check` 7, `css-vars:check` 6, none with arguments. The exact forms were added alongside the wildcards rather than widening either.
- Deliberately still absent: `yarn build` and `yarn test:e2e` write output, `eslint:write` and `prettier:write` rewrite files, and `npx`/`node`/`python3` would grant arbitrary code execution. `git push`, `rebase`, `remote` and `worktree` remain prompts by choice.
