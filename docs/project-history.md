## 2026-08-16 — Correct two claims the split's own CI run disproved

- **A missing report on `main` does not block `codecov/patch`.** The entry below stated the required check depends on both Codecov having the repository active _and_ `main` carrying a report for the comparison to have a base. The first half is right and is the one that bites; the second was inference, and [#189](https://github.com/henetiriki/portfolio/pull/189) disproved it by passing while `main` still carried the dropped upload. Worth knowing before it sends someone after a problem they do not have.
- **The ruleset has no bypass actors, and the publication entry still said it did.** The entry was accurate when written: the Repository admin role held an `always` bypass from 12:14, and it was removed at 13:04 the same day — visible in `gh api repos/<owner>/<repo>/rulesets/<id>/history`, which is the only place that change is recorded anywhere. The entry is now marked superseded rather than corrected, because it described the state at the time, and the reasoning for the removal is [D-260816c](decisions.md#d-260816c--keep-the-ruleset-free-of-bypass-actors-and-accept-the-wedge-risk). It surfaced because renaming the required check briefly put the repository in exactly the wedge the bypass had been there to prevent.
- **A change made outside git is now explicitly a change**, in [`AGENTS.md`](../AGENTS.md) and in the documentation sweep. This is the root cause of both mismatches above rather than a separate lesson: settings work produces no commit, so nothing drags the sweep along behind it the way editing a file does, and the discipline that already works for code never fires. `AGENTS.md` also now says to verify live state before picking up a roadmap item that names a setting, which is two commands.

Deliberately two: the release checklist is worked through before the pull request exists, and these are the only items an agent cannot answer for itself. A `.github/pull_request_template.md` would not have worked, because `gh pr create --body-file` bypasses templates; the checklist costs nothing at merge time because `squash_merge_commit_message` is `COMMIT_MESSAGES`, so it never reaches the history.

Nothing else in the repository records a settings change.

## 2026-08-16 — Split CI into concurrent jobs, and require `codecov/patch`

- **`Validate & build` is replaced by three jobs**: `Classify the change`, then `Validate` and `Build & browser suite` running concurrently. Lint, types, formatting and the unit suite no longer wait behind a production build and a ~270 MB Playwright download. The rationale, including why the classification needs a job of its own, is [D-260816b](decisions.md#d-260816b--split-ci-into-concurrent-jobs-with-the-classification-in-its-own).
- **The `env:` block is hoisted to workflow level**, so a naive duplication across both jobs — and the next variable added to only one copy — never had a chance to happen. `id-token: write` moved the other way, from the workflow to just the `Validate` job that uploads coverage, since nothing else needs it.
- **The ruleset now requires `Validate`, `Build & browser suite` and `codecov/patch`**, applied in the same window as the merge. A rule naming a check that no longer runs blocks every pull request indefinitely, which is why the two roadmap items that owned this landed together rather than in sequence.
- **Codecov deactivates a repository when its visibility changes, and the failure is silent.** The upload for `bf6f364` logged `Upload queued for processing complete`, the step succeeded, the job went green — and Codecov's API has no such commit. Nothing in the workflow, the job log or GitHub reveals it; the CLI cannot tell a dropped upload from a stored one. Making the repository public is exactly the moment this fires, and exactly the moment nobody is watching coverage.
- **Requiring `codecov/patch` therefore has a dependency outside the repository.** Not merely "the upload must run", but "Codecov must have the repository active" — which is not visible from here. [Testing](development.md#testing) now records how to check that directly against Codecov's API, because the workflow is the wrong place to look and the obvious place to start.
- **Three documents contradicted the ruleset** and were corrected: [D-260815c](decisions.md#d-260815c--give-documentation-only-changes-a-cheap-ci-path-rather-than-no-ci-run) still said nothing was required, [Development Workflow](development.md#testing) described requiring the check as a future step in one paragraph while asserting it was required in another, and [`AGENTS.md`](../AGENTS.md) still described the cheap path as "install and `prettier:check`, nothing else" — stale since the entry below.
- **A renamed decision identifier is now explicitly retired rather than recycled.** `D-260816a` was published before becoming [D-260815i](decisions.md#d-260815i--wait-for-the-chromium-fix-instead-of-working-around-the-android-navigation-bar), so this decision is `D-260816b`; reusing the letter would have pointed stale links at an unrelated entry, which is the outcome renaming-in-place existed to avoid.
- **A sanity pass over the newly public repository found nothing else wrong.** Every relative link and heading anchor across the documentation resolves, both committed `.env` files hold only non-secret values, there are no Actions secrets, secret scanning reports nothing, and the README badges and every `henetiriki/portfolio` URL are live. The CodeQL default setup was the one undocumented thing found, and is now a roadmap item rather than a surprise.

## 2026-08-16 — Restore the Jest run and the Codecov upload to the cheap path

- **Both now run on every pull request, including a documentation-only one**, which is what makes `codecov/patch` requirable: a skipped upload posts no status at all, and a required check that never reports leaves the pull request pending forever. That was the last thing standing between the protected branch and the check set originally planned — [D-260815c](decisions.md#d-260815c--give-documentation-only-changes-a-cheap-ci-path-rather-than-no-ci-run).
- **The cheap path is otherwise unchanged.** Lint, both type-checks, `css-vars:check`, the production build, the Playwright browser download and the browser suite are still skipped on prose, which is where the saving actually was. The unit suite runs in seconds; the browser half is the expensive part.
- **Prose still cannot affect Jest** — the run is paid for so the requirement holds, not because a documentation change might break a test. `prettier:check` remains ungated for the opposite reason: it is the one check that _does_ apply to what changed.
- **The fork exception stays**, since GitHub issues no OIDC token to a fork pull request and `fail_ci_if_error` would turn a missing token into a failed job.

## 2026-08-16 — Make the repository public and protect `main`

- **The repository is public**, which is what made required status checks available at all: they are unavailable to a private repository on a free personal plan, and publishing was chosen over a paid plan. The two pre-publish checks were discharged first — see the entry below.
- **`main` is protected by a ruleset** requiring a pull request, squash merges only, `Validate & build` passing, and branches to be up to date before merging. Force pushes and branch deletion are blocked. The repository role was on the bypass list, because a solo maintainer with no second person to unblock them should not be able to wedge themselves out of their own repository — _superseded the same day: the bypass was removed a little under an hour later, and the reasoning is [D-260816c](decisions.md#d-260816c--keep-the-ruleset-free-of-bypass-actors-and-accept-the-wedge-risk)._
- **`codecov/patch` is deliberately not required yet.** It cannot post on a documentation-only pull request while the cheap path skips the upload, so requiring it now would leave those pull requests pending forever. The [Roadmap](roadmap.md#testing--automation) carries the restore that unblocks it.
- **Requiring branches to be up to date mechanises a caveat [`AGENTS.md`](../AGENTS.md) previously had to state.** Two branches that each pass alone and break together now have something to catch them, rather than depending on whoever rebases second remembering to re-run validation.
- **Secret scanning, push protection, Dependabot alerts and security updates, and private vulnerability reporting are enabled** — all free only on a public repository, and none of them available before. Push protection is the one that changes daily behaviour: a recognised credential is refused at the push rather than found afterwards. `CONTRIBUTING.md` now points security reports at the private advisory route first.
- **Fork pull request workflows require approval from all external contributors**, and Vercel's Git Fork Protection was already on by default, so neither CI nor a preview deployment runs on someone else's code unattended.
- **Actions defaults were tightened while the settings were open**: the default workflow token dropped from write to read, and Actions can no longer create or approve pull requests. Neither affects `ci.yml`, which declares its own `permissions:` block; both close the gap for anything added later that forgets to.

## 2026-08-15 — Enforce the Content Security Policy, and stop the service worker rewriting it

- **The policy now ships as `Content-Security-Policy`.** Report-Only is retired rather than run alongside, and the planned intermediate step of enforcing only the inline-independent directives was skipped as an obsolete hedge — [D-260815h](decisions.md#d-260815h--promote-the-policy-to-enforcing-in-one-step). Current behaviour in [Security](security.md#content-security-policy).
- **A real observation window produced thirteen violations over all five pages**, reducing to four distinct causes. Two were the predicted allowlist gaps: `script-src` gained `'wasm-unsafe-eval'` for the WebAssembly module Maps compiles, and `connect-src` gained `https://mapsresources-pa.googleapis.com` for its style tables. The 2026-08-14 `next dev` forecast proved sound in production.
- **The other nine were a mechanism, not a gap.** A request the service worker handles is re-issued from inside the worker, where `connect-src` is the only fetch directive that applies — so Serwist's `defaultCache`, which ends in a catch-all, quietly made `connect-src` govern every subresource on the site. The worker now caches same-origin requests only, which removes the class of problem rather than widening the policy — [D-260815f](decisions.md#d-260815f--cache-only-same-origin-requests-so-the-service-worker-stops-rewriting-the-policy).
- **`/_offline` had never been precached, and the offline fallback had never worked** for a route the worker had not already seen. The generated manifest carries the page's JavaScript chunk but not its prerendered HTML, so `matchPrecache` always returned `undefined`. Confirmed pre-existing by rebuilding against the unmodified worker — [D-260815g](decisions.md#d-260815g--precache-the-_offline-document-which-the-build-manifest-omits).
- **The manual check could not have caught it.** A page you have already visited is answered from the runtime cache without the fallback being consulted, so testing offline on a page you just loaded passes regardless. `service-worker.spec.ts` now covers both directions, which is why there are two tests rather than one.
- **Verified across Chromium, Firefox and Safari** on the preview deployment, with the map driven until it rendered in vector mode and the YouTube embed actually played. Beyond reports, the Chromium pass showed all three worker caches holding zero cross-origin entries and the precache carrying `/_offline` as a document.
- **Safari's `frame-ancestors` message turned out to be spec behaviour**, not a finding: it follows [CSP Level 2](https://www.w3.org/TR/CSP2/#directive-frame-ancestors) and discards the directive in a report-only policy, so that directive could never have been observed and was promoted on `X-Frame-Options: DENY` having enforced the identical rule throughout.
- **The Map ID was missing from the preview environment**, which is what made the first verification attempt meaningless — the map fell back to raster and never made the style-table request. `next.config.js`'s `env` bridge silently emits no substitution for a variable undefined at build time, leaving a runtime lookup that resolves to `undefined`, and the `as string` cast in `mapConfig.ts` means nothing complains.
- **`src/server/csp-mail/` is deleted with the window it existed for**, along with `CSP_VIOLATION_EMAILS` and its `.env.test` and CI entries. The endpoint, its size cap, its extension filtering and its logging all remain.

## 2026-08-15 — Diagnose the Android gesture-bar band, and change nothing

- **No code changed.** The white band behind the Android gesture bar is a Chromium defect whose fix merged upstream on 2026-08-06 and colours that bar from `theme_color`, already `#080a20` here — so the manifest keeps `display: standalone` and the band should clear itself. Rationale in [D-260815i](decisions.md#d-260815i--wait-for-the-chromium-fix-instead-of-working-around-the-android-navigation-bar), the check to run in the [Roadmap](roadmap.md#performance-seo--platform-polish).
- **The band was introduced by [#134](https://github.com/henetiriki/portfolio/pull/134)**, which switched `display` from `fullscreen` to `standalone` in the same commit that changed `background_color` to `#080a20`. Under `fullscreen` — the behaviour since [#32](https://github.com/henetiriki/portfolio/pull/32) — Android draws no system bars, so there was no navigation bar to mis-paint.
- **[D-260815d](decisions.md#d-260815d--paint-the-document-canvas-on-html-not-on-body) is corrected in place rather than left standing.** It claimed Chrome derives the gesture-bar region from the document canvas — true of a browser tab, false of an installed app. The opaque `html` background is correct on its own merits and stays, but it never addressed the reported symptom, and production serving `html: rgb(8, 10, 32)` with the band still present is what proved it.
- **Two workarounds were built and both discarded.** A revert to `fullscreen` was written, validated and ready to commit; `viewport-fit=cover` was abandoned mid-implementation. Both were dropped once the upstream fix turned out to be ten days old rather than five years — **a permanent workaround for a temporary defect outlives the bug**, because nobody remembers to remove it.
- **The ticket was nearly cited without being read.** An earlier draft referenced [issues.chromium.org/40759522](https://issues.chromium.org/issues/40759522) on the strength of a search-result title, then misread its 2021 filing date as the age of the fix. The tracker needs a sign-in and could not be read by tooling; the owner read it, which is what turned the decision around.
- **A stale roadmap item left behind by [#179](https://github.com/henetiriki/portfolio/pull/179) is removed**: the duplicated-maskable-icons question it described was answered by that change, which split `any` and `maskable` into separate files.

## 2026-08-15 — Stop rediscovering that the shell-hygiene hook refuses prose

- [`AGENTS.md`](../AGENTS.md) now requires commit messages and pull request bodies to be written to a file and passed with `git commit -F <file>` or `gh pr create --body-file <file>`, never an inline heredoc. [D-260814b](decisions.md#d-260814b--enforce-shell-hygiene-with-a-hook-rather-than-a-convention) carries the correction that prompted it.
- **The documented casualty was the rare one.** The hook tests the entire command string, and the limit was illustrated with `find … -exec … \;`, which implied collisions were occasional. A heredoc body is part of that string too, so a single semicolon anywhere in a commit message refuses the commit — and this project asks for long prose messages, so one usually appears. Every new session hit it, diagnosed it, and worked around it identically.
- **The hook was not narrowed, deliberately.** Ignoring text after a `<<` marker would have stayed textual and needed no shell grammar. It was rejected because the Auto-mode revision to the same decision promotes this hook from an ergonomic measure to the control that keeps the allow and deny lists honest, and a heredoc is exactly where an evasion would hide. Writing the message to a file is better practice regardless — reviewable before it runs, for the same reason `Write` beats a heredoc for file changes.
- **`D-260814b`'s stated cost was wrong and is corrected in place** rather than left standing: it claimed parsing would save "a handful of commands a year". The docs describe what is true today, and that sentence had been falsified by use.

## 2026-08-15 — Give documentation-only changes a cheap CI path

- `ci.yml` classifies each change with one `git diff` and gates every expensive step behind it. A change touching only `docs/`, `*.md`, `.claude/` or `.worktreeinclude` installs dependencies, runs `prettier:check` and stops. Behaviour on the [release checklist](release-checklist.md#pull-request), rationale in [D-260815c](decisions.md#d-260815c--give-documentation-only-changes-a-cheap-ci-path-rather-than-no-ci-run).
- **A third of recent runs were buying nothing, measured rather than assumed.** Replaying the classification over the thirty merges to `main` up to [#175](https://github.com/henetiriki/portfolio/pull/175): **ten take the cheap path**, including the two most recent documentation pull requests and the shell-hygiene hook change ([#164](https://github.com/henetiriki/portfolio/pull/164)), which touched only `.claude/settings.json` and `AGENTS.md`.
- **The same replay is what proves the exclusion list is CI's and not Vercel's.** [#173](https://github.com/henetiriki/portfolio/pull/173) takes the full path on `e2e/` alone — the change Vercel skips and CI most needs to run — and [#166](https://github.com/henetiriki/portfolio/pull/166) takes the full path on `.gitignore` alone, which is deliberately in neither list.
- **The job still runs and still reports**, because the filter is a per-step `if:` rather than `paths-ignore`. A filtered-out workflow never reports, and a required check that never reports leaves a pull request pending forever — which would have quietly broken the branch protection the [Roadmap](roadmap.md#testing--automation) plans, before it was ever switched on.
- **`prettier:check` is the one step never gated**, since `prettier .` covers the whole tree and is the only check that applies to a prose change at all.
- **Skipping the Jest run has a consequence for branch protection, now written into the item that owns it.** No coverage report is uploaded, so `codecov/patch` is not expected to post on a documentation-only pull request; requiring it needs checking against a real one first. Nothing is required today, so nothing is broken today.
- **`fetch-depth: 2` is load-bearing.** The default shallow checkout has no `HEAD^` to diff against. The command fails open in that case and in every other — a failure classifies the change as not documentation-only — so the failure mode is a needless full run, the same direction `vercel.json` chose.

Off unless `CSP_VIOLATION_EMAILS` is exactly `true`. ## 2026-08-14 — Stop `git -C` from defeating the permission allowlist

- [`AGENTS.md`](../AGENTS.md) gains a shell-hygiene rule against passing `-C <path>` to `git`, and `.claude/settings.json` gains the bare no-argument forms of the four read-only check scripts plus `git check-ignore` and the browser `find` tool.
- **Found from the symptom, not from a review.** Git commands started prompting for approval again, and the allowlist looked untouched because it was — the commands had changed shape. `Bash(git add *)` matches by prefix and never sees `git -C /path/to/repo add`, and the harness's own auto-allow for read-only git reads the token after `git`, finding `-C` rather than `status`. Ten `git -C … status` calls, seven `log`, seven `grep` and five `commit` in one session all fell through to a prompt.
- **The habit came from avoiding `cd`.** The rule that the working directory persists between calls is what makes `-C` pointless, so reaching for it to honour that rule inverts it. Both defeat the allowlist for the same reason chaining does: matching runs against the whole command string.
- **Widening the rules was rejected as the fix.** `Bash(git -C * )` would allowlist `push --force` and `reset --hard` along with everything else, and per-subcommand `-C` variants would double the list to accommodate a habit with no reason to exist.

The exact forms were added alongside the wildcards rather than widening either.
- Deliberately still absent: `yarn build` and `yarn test:e2e` write output, `eslint:write` and `prettier:write` rewrite files, and `npx`/`node`/`python3` would grant arbitrary code execution. `git push`, `rebase`, `remote` and `worktree` remain prompts by choice.

## 2026-08-14 — Remove the WITH_PWA flag

- Every production build now generates the service worker and development never does, with no flag to set anywhere. `.env.production` held only `WITH_PWA=true` and has been deleted; the variable is also gone from `.env.test`, the CI workflow and the Vercel project. CI drops from two builds to one, and the release checklist from two build steps to one. See [D-260807a](decisions.md#d-260807a--generate-the-service-worker-in-every-production-build-never-in-development).
- **The gate is `NODE_ENV`, not Serwist's own `disable` option**, and that distinction is load-bearing. `withSerwistInit` attaches a `webpack` key to the config unconditionally — `disable` is only consulted inside that callback — so wrapping unconditionally would put a webpack config in front of `next dev`, which runs Turbopack and which `@serwist/next` explicitly warns it does not support. Returning early before the dynamic `import()` keeps Serwist out of development entirely. Verified by reading the plugin source rather than trusting the option name.
- CI's "no service worker without `WITH_PWA`" assertion was **removed rather than left in place**, since the gating it tested no longer exists and a step that can no longer fail is worse than no step.
- Playwright now blocks service workers (`serviceWorkers: 'block'`). The suite serves a production build, which always ships a service worker now, so an unblocked one would precache pages and let a later spec pass against a stale response from an earlier one.

## 2026-08-11 — Defer the YouTube embed on /experience

- `/experience` scored materially worse than every other route in PageSpeed mobile. Measured against the live site: the YouTube iframe was eager (no `loading` attribute) and sits at 35,207px down a 39,453px document, so a full `youtube.com/embed` player — roughly a megabyte of JavaScript — was fetched and executed on every page load for content almost nobody scrolls to. Page markup was not the problem: only 522 DOM nodes.
- `/travel` was the diagnostic control rather than a counter-example. It carries a heavier third-party in the Google Map, but that is code-split via `next/dynamic` and only initialises once in view, and it scores well. Same class of dependency, opposite loading strategy.
- Fixed with `loading='lazy'`. The existing `width`/`height` already reserve the box, so deferring introduces no layout shift.
- **Confirmed after deploying:** mobile PageSpeed for `/experience` returned **Performance 93, Accessibility 98, Best Practices 100, SEO 100**, from a consistently poor performance score. This validates the diagnostic method as much as the fix — `/travel` was used as a control (a heavier third-party that is deferred and scores well), which predicted the cause before any change was made.
- Covered at both levels: a unit test asserts the attribute and the reserved dimensions, and browser specs assert the _behaviour_ — no YouTube request on initial load, but one once the iframe is scrolled into view, so a "fix" that simply broke the embed would not pass. Requests are stubbed rather than allowed through, so the suite gains no dependency on YouTube being reachable. Both guards were verified to fail with the attribute removed.
- **Retracted, 2026-08-13:** this entry originally reported that the fixed background image was requested twice on every route (`_next/image?…&w=640` and again at `&w=3840`), and a roadmap item was raised to investigate it. That was wrong. Re-measured on the live site at a real 375×812 mobile viewport: `/api/img-id` is called **once**, exactly **one** `_next/image` request is made, and it is `w=750` — precisely 375 × DPR 2. The original reading came from a browser pane reporting a `0×0` viewport, which made the browser select a small `srcset` candidate and then re-select the largest once layout resolved. One image at two widths, not two fetches. The roadmap item has been removed. The earlier React-hook defect that genuinely did fetch the background twice remains fixed; a recurrence would show two `/api/img-id` calls and two different image ids, and neither is present.
